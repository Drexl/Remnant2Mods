## 2. Toolchain Landscape (initial research pass)

### Engine
- Remnant 2 runs on Unreal Engine 4/5-family, using **IOStore** (`.ucas`/`.utoc` files present in the Paks folder). This matters because it changes the packaging process — old-style loose `UnrealPak` packaging isn't enough; you need chunk assignment / IOStore-aware cooking if you go the full asset-replacement route.

### Primary source used for general UE modding literacy
- [Dmgvol/UE_Modding](https://github.com/Dmgvol/UE_Modding) — general-purpose UE4/5 modding guide collection, not game-specific. Structure:
  - **TheBasics/** — extracting game files, browsing assets, exporting models/animations
  - **BasicModding/** — changing Blueprint default values, editing `.umap`s (via tool called "Stove" — supports duplicating actors, editing spawn-instance default values)
  - **IntermediateModding/** — creating a matching UE project (must be named exactly like the game's project — check the game's largest `*-Shipping.exe` for the binary name), packaging/cooking settings (must disable "Share Material Shader Code"), dummying/replacing assets (textures, materials, meshes, skeletal meshes)
  - **AdvancedModding/** — **injecting custom Widgets into game menus using Blueprints** (this is the technique most relevant to loadout-naming and inventory search bar), speedrun/randomizer/trainer-style logic
  - **BPModding/WorkingWithML.md** — explains mod loader conventions: UML and UE4SS use DLL injection; DML is a pak-based loader needing no third-party software. BP mods live at `/Mods/<ModName>/`, main blueprint must be named `ModActor`, uses `PreBeginPlay`/`PostBeginPlay` (or default `BeginPlay`) lifecycle methods.
  - Tools referenced: UAssetGUI, UAssetAPI (by atenfyr), UnrealModLoader (by RussellJerome)
  - Caveat: this guide is generic across UE games — Remnant 2-specific class names, widget hierarchies, and save structures are **not** in this guide and must come from community/Discord/reverse engineering.

### Remnant-2-specific tooling (from broader web research)
- **RE-UE4SS** ("UE4SS") — injectable Lua scripting system + SDK generator + live property editor for UE4/5 games. This is the dominant modding backbone for Remnant 2 specifically. GitHub: `UE4SS-RE/RE-UE4SS`.
- **"Allow Asset Mods"** (Nexus Mods, remnant2/mods/2) — the de facto required base install for the Remnant 2 modding scene. Bundles:
  - A custom/unreleased build of UE4SS
  - A console enabler
  - A blueprint mod loader
  - Install path: extract into `Steam\steamapps\common\Remnant2\Remnant2\Binaries\Win64` (or WinGDK path for Xbox/Game Pass)
  - Config toggle: `Remnant2\Remnant2\Binaries\Win64\Mods\mods.txt` — set lines to 0 to disable console enabler or BP mod loader individually
  - Notes pak-only config-edit mods do **not** affect multiplayer join ability; DLL-injection-based mods (like this one) have occasionally caused compatibility hiccups (e.g., a period where `xinput1_3.dll` caused startup crashes for some users, fixed by community workaround / later patched)
  - Steam Deck/Linux: not officially supported as of source mod's writing; there's a beta UE4SS build referenced for Linux/Deck compatibility
- **Community Discord**: `discord.gg/jX5qd2RefK` — described as the hub "to discuss Remnant 2 and other Gunfire Games modding." This is likely where actual class paths, widget names, and save-data structure knowledge is shared, since it isn't published in any single guide.

Nearly all of these are **UE4SS Lua script mods** — folder structure is consistently `Mods/<ModName>/Scripts/main.lua` (+ `config.lua`, `enabled.txt`, sometimes a `.dlls/main.dll` C++ variant):

## 3. Pull-Apart Task: How existing Remnant 2 Lua mods actually work

### 3.1 The core UE4SS Lua API (the actual mechanism, not just folder structure)

This is the piece the earlier pass was missing — *how* a Lua mod reaches into the game at all. Four functions do almost all the work across every example found (Remnant 2, Palworld, Hogwarts Legacy modding docs all converge on the same pattern, confirming it's a general UE4SS idiom, not per-game magic):

- **`StaticFindObject(path)`** — finds an object (usually a *class default object*, e.g. `Default__SomeItem`) that already exists in memory by its full path. Used to read/write default property values directly.
- **`RegisterHook(path, callback)`** — hooks a `UFunction` so `callback` fires after it runs. **Critical constraint: the target UFunction must already exist in memory when you register the hook** — this is why almost every mod hooks `/Script/Engine.PlayerController:ClientRestart` first (fires on character spawn/respawn, both singleplayer and co-op), and does its real work *inside* that callback.
- **`NotifyOnNewObject(path, callback)`** — fires whenever a new instance of a class is constructed. Unlike `RegisterHook`, the class does **not** need to exist yet when you register it. This is how mods reliably catch dynamically-created things — including **UI widgets that don't exist until a menu opens** — which is exactly the mechanism our loadout/search-bar mods will need.
- **`ExecuteInGameThread(fn)`** — wraps the actual mutation logic; property/function calls on live UObjects generally need to happen on the game thread.

Common nesting pattern seen across every real-world example (Palworld docs, Hogwarts Legacy community scripts, and the Remnant 2 "ModifyStat" reference below all use this same shape):

```lua
RegisterHook("/Script/Engine.PlayerController:ClientRestart", function(Context, NewPawn)
  ExecuteInGameThread(function()
    -- do the actual work here, now that we know a player/world exists
    NotifyOnNewObject("/Game/Path/To/SomeWidget.SomeWidget_C", function(WidgetInstance)
      -- runs every time that specific widget is constructed (e.g. menu opened)
    end)
  end)
end)
```

### 3.2 Real Remnant 2 example (from a community "Modding 101" README, ShadowChaosTime/Nexus mod #167, crediting AuriCrystal & "Pokémon Professor Vokun")

This is a genuine beginner-facing script-mod tutorial from the R2 community, with a concrete working example — worth treating as closer to ground truth than the generic Dmgvol guide for R2-specific paths:

```lua
function ModifyStat (asset, name, value)
  local Item = StaticFindObject(asset)
  if not Item:IsValid() then return end
  Item:SetPropertyValue(name, value)
end

RegisterHook("/Script/Engine.PlayerController:ClientRestart", function(self, NewPawn)
  ExecuteInGameThread(function()
    ModifyStat(
      "/Game/World_Nerud/Items/Trinkets/Amulets/Hyperconductor/Amulet_Hyperconductor.Default__Hyperconductor",
      "HeavyWeaponAmmoMod",
      69
    )
  end)
end)
```

What this teaches us concretely:
- **Real R2 asset path structure confirmed**: `/Game/World_<Zone>/Items/<Category>/<Subcategory>/<ItemName>/<AssetFile>.Default__<ClassName>` — e.g. amulets live under `/Game/World_Nerud/Items/Trinkets/Amulets/...`. Rings appeared elsewhere in our search results as `/Game/World_Base/Items/Trinkets/Rings/...`. This gives us a real naming convention to anticipate when we go hunting for loadout-related classes.
- `SetPropertyValue(name, value)` is the write path for simple property edits on a found object — this is likely how a "loadout slot count" constant could be patched *if* it's exposed as a simple property on some default object, rather than buried in UI layout.
- The mod loader folder convention is confirmed independently: `Mods/<ModName>/enabled.txt` + `Mods/<ModName>/Scripts/main.lua` (capital-S "Scripts" appears in most real mods; lowercase "scripts" appears in this beginner README — both seem to work, but match what a given base install expects).

### 3.3 Discovery tooling — how modders actually find these paths (we don't get to guess)

The "Modding 101" README and other sources converge on the same toolchain for figuring out class/property names before writing any hook:

- **FModel** (fmodel.app) — asset browser/dumper for UE .pak/.ucas/.utoc archives. Modders use a community-shared **mapping file** (`.usmap`) specific to Remnant 2, distributed via the modding Discord, to get FModel to resolve real property/class names instead of obfuscated ones. Right-click → "Save Folder's Packages Properties .JSON" dumps parsed structure to JSON, which can then be searched with a text editor/regex.
- **UE4SS Live View / debugger** — built into UE4SS itself. Lets you browse live Blueprint instances *while the game is running* and see real property values and paths, including UI widget hierarchies. This is the recommended way to find the specific widget class name for something like the loadout screen, since it's live and in-context rather than static-file archaeology.
- **UE4SS SDK generator** — can dump a full C++-style SDK of the game's UE classes, useful as a searchable reference once generated for our specific installed game version.

**Practical conclusion for our 3 mods**: before writing a single hook, we need to (1) get UE4SS running with Live View enabled, (2) get FModel + the community R2 mapping file, and (3) actually open the loadout screen and inventory screen in-game with Live View active to find the real widget class names, property names, and array sizes involved. No guide — generic or R2-specific — is going to hand us the literal loadout-widget class name; that's a "go look at the live object tree ourselves" task, ideally cross-checked against the modding Discord in case someone's already documented it.

### 3.4 CONFIRMED — Live inspection of `LoadoutComponent` (loadout slot count)

Live Lua inspection (via `FindAllOf("LoadoutComponent")` + reading `.Slots` array on the character's live component, using `ZZTestMod` as a scratch script, since UE4SS's Live View GUI only exposes *reflection metadata* for FProperty nodes — offsets/flags/types — not actual runtime values; needed to read via Lua + log instead) on the player character's live `LoadoutComponent` (`/Game/Maps/Main.Main:PersistentLevel.Character_Master_Player_C_<instanceID>.Loadout`) confirmed:

- `LoadoutComponent.Slots` has exactly **one entry**, `Template = /Game/_Core/Loadouts/Gear_Loadout` (a `LoadoutTemplate` asset), with **`NumRecords = 11`**.
- **CORRECTED (was wrong above, then re-corrected): the in-game UI actually shows 8 saveable loadout slots, plus one additional non-saveable "Last Gear State" slot** (visually confirmed by the user in-game) — not 3, as originally assumed going into this investigation. That's 9 visible slots against a cap of 11 — much closer to the data-layer limit than first thought.
- **Revised hypothesis, replacing the "pure UI problem" theory above**: since the visible slot count (8, or 9 counting "Last Gear State") tracks so closely with `NumRecords = 11`, the UI panel (`Widget_LoadoutsPanel_C`) is very likely **already dynamically built from `NumRecords`/a related count function** (e.g. `GetMaxRecordsForTemplate`), rather than hardcoded to a fixed tile count. If true, this is great news: mod #1 may reduce to the "easy property patch" case flagged as best-case back in section 3.2 — i.e. **just increasing `NumRecords`** (wherever that value actually originates — see open question below) could make the existing UI panel render more slots automatically, with no widget/layout work needed at all.
- **New critical open question, superseding the "is the UI hardcoded" question below**: where does `NumRecords = 11` actually come from? Options: (a) a property directly on the `Gear_Loadout` `LoadoutTemplate` asset (easy `SetPropertyValue` patch, same pattern as the amulet example in 3.2), (b) computed elsewhere in `LoadoutComponent` logic (e.g. based on DLC ownership/unlocks), or (c) a hardcoded engine-side constant. Needs tracing — likely via FModel on the `Gear_Loadout` asset itself, or via `GetMaxRecordsForTemplate`'s Blueprint graph if it's not a plain property.
- Also found: `Widget_LoadoutsPanel_C` at `/Game/UI2/UI_Widgets/UI_Game/UI_Game_Character/Widget_LoadoutsPanel.Widget_LoadoutsPanel_C` — has its own `GetLoadoutComponent()` function, same pattern as `Widget_Loadout_C` (the per-tile widget). Strong candidate for the parent container that lays out the 3 visible loadout tiles. Not yet inspected for whether its child list is a hardcoded fixed-size layout or a loop over an array/count.
- Minor unexplained curiosity, not yet investigated: two live `LoadoutComponent` instances showed up in the same query, on two different `Character_Master_Player_C` instance IDs, both with identical `Slots` data. Possibly a listen-server client/server duality (even singleplayer R2 runs as a local listen server) rather than two real characters — not blocking, but worth keeping in mind if duplicate-instance confusion shows up again.

### 3.4f CONFIRMED — `Widget_LoadoutsPanel_C.Refresh` builds tiles from `GetMaxRecordsForTemplate`, not raw `NumRecords`

FModel property-JSON dump of `Widget_LoadoutsPanel_C` (`Widget_LoadoutsPanel.json`, saved to repo root) confirms this widget's `Refresh` function is the real tile-count driver. It's a reflection-only dump (temp-variable names from the compiled function, not the visual graph), but the naming makes the flow readable:

1. `CallFunc_GetLoadoutComponent_Loadouts` → gets the live `LoadoutComponent`.
2. `CallFunc_GetMaxRecordsForTemplate_ReturnValue` → calls a `GetMaxRecordsForTemplate`-named function (not a raw `NumRecords` field read).
3. `CallFunc_Subtract_IntInt_ReturnValue` → `CallFunc_Clamp_ReturnValue` → some adjustment/clamping of that count.
4. `CallFunc_GetChildrenCount_ReturnValue` compared against the clamped count, then a loop: `CallFunc_Create_ReturnValue` (creates a new `Widget_Loadout_C` tile) → `CallFunc_AddChild_ReturnValue` (adds it to the panel) for each tile still missing.

**This explains the earlier "NumRecords=20 write did nothing" result**: the UI never reads `Slots[].NumRecords` directly — it goes through `GetMaxRecordsForTemplate`, a function call that may or may not simply return `NumRecords` under the hood. This is the real mod #1 hook candidate.

**Next test**: call `GetMaxRecordsForTemplate` from Lua on the live `LoadoutComponent` (same reflection-call pattern already proven safe for `GetDisplayNameForLoadout`) and log its return value — both before and after patching `NumRecords` — to see whether it tracks the raw field or is computed/capped independently (e.g. by DLC ownership or a hardcoded constant). If it just proxies `NumRecords`, the timing of our earlier test is the likely culprit (patched after `Refresh` had already run once) and a hook that patches *before* the panel opens should work. If it's independent, we'll need to find where its own value comes from.

### 3.4g CONFIRMED — `GetMaxRecordsForTemplate` directly proxies `NumRecords`

Test result (both `LoadoutComponent` instances, no crash):

```
Slot 1: GetMaxRecordsForTemplate (before patch) = 11
Slot 1: patched NumRecords to 20
Slot 1: GetMaxRecordsForTemplate (after patch) = 20
```

The function is a pure passthrough of the raw field — not independently capped by DLC/unlocks/a hardcoded constant. **This means the earlier "NumRecords=20 write had no visible UI effect" result was a stale-UI/timing artifact, not a wrong hypothesis.** The write happens on `ClientRestart`, but if the Loadouts screen widget was never freshly (re)constructed after that write during that test, `Refresh` wouldn't have re-run against the new value.

**Mod #1 is very likely just a `NumRecords` property patch after all** — the originally-hoped-for easy case. Next step: retest cleanly — patch `NumRecords` on `ClientRestart` (already happening in `ZZTestMod`), then explicitly open the Character > Loadouts screen for the *first time that session* (not just re-checking a screen that was already open/cached before the patch) and see if more than 8 saveable slots appear.

### 3.4h CONFIRMED (superseding 3.4g's optimism) — tile count is hardcoded to 8, independent of `NumRecords`/`GetMaxRecordsForTemplate`

Retested cleanly per 3.4g's plan: full relaunch, `NumRecords` patched to 20 on `ClientRestart`, then opened the Loadouts screen fresh. **Still only 8 saveable slots** — no change.

To find out *why*, searched UE4SS Live View for all live `Widget` instances while the loadout overlay was open (search "Widget", with "Include CDOs" unchecked and "Instances only" checked to filter out templates/defaults — results dumped to `WidgetSearchResults.txt`, ~10.8MB, too large to read directly; grepped for `Loadout`). Findings:

- `Widget_LoadoutsPanel_C` is confirmed genuinely live, nested at `Widget_Character_C → Widget_Equipment_Stats_C → Widget_LoadoutsPanel_C` — real hierarchy, not a guess. Strongly suggests the double-tap-R quick-access overlay is a shortcut into this same underlying Character-menu widget tree, not a separate implementation (not fully proven, but no longer a live risk to the investigation).
- Exactly **8** live `Widget_Loadout_C` tile instances exist at runtime (`Widget_Loadout_C_2147477340`, `_320`, `_300`, `_280`, `_260`, `_240`, `_220`, `_200` — sequential creation order, spaced by 20, parented directly to `BP_RemnantGameInstance_C` as is typical for freshly-`CreateWidget()`'d widgets before `AddChild` reparents them), plus one separate `LastLoadoutSlot` instance for the 9th non-saveable tile.
- **This confirms the `Refresh` function's `Subtract`/`Clamp` step (3.4f) hardcodes a max of 8 tiles**, independent of `GetMaxRecordsForTemplate`'s actual return value (confirmed correctly returning 20 in 3.4g). The loop simply never runs past 8 iterations, regardless of what the live data says the cap should be.

**What this means for mod #1**: the clamp is baked into the compiled Blueprint function (a literal pin value on a `Clamp` node), not a property we can patch with `SetPropertyValue`. A direct data patch isn't enough — we need a **behavioral hook**: `RegisterHook` on `Widget_LoadoutsPanel_C:Refresh` (pre or post) and, from Lua, manually call `CreateWidget`+`AddChild` extra times to mimic what the loop does for indices 8+, OR find whatever function underlies `Clamp`'s literal max and intercept/override its return via a hook rather than editing the property. Both need the `Refresh` function's actual container/parent-slot logic understood a bit more first (which panel/container the new tiles get added to, and whether that container's layout supports more than 8 without additional layout work).

### 3.4i CONFIRMED — the tile container has a hardcoded fixed height too (`SizeBox_0.HeightOverride = 688`), no `ScrollBox` anywhere

Traced the widget tree (not the function, the static design-time hierarchy) to find where `Refresh`'s `AddChild` calls actually land: a `VerticalBox` named `LoadoutList`, which has **zero static/design-time children** — it's populated entirely at runtime by the loop. `LoadoutList` sits inside a `SizeBox` (`SizeBox_0`) with `HeightOverride = 688.0` and `bOverride_HeightOverride = true` — a hardcoded fixed pixel height. Grepped the whole file for `ScrollBox`: **none exists** anywhere in this widget's tree.

**Implication**: even after successfully hooking `Refresh` to create more than 8 tiles, they'd overflow `SizeBox_0`'s fixed 688px bound rather than scroll — `SizeBox` doesn't clip by default, so extra tiles would likely spill out visually past the box rather than simply being invisible, but either way it'd look broken without a fix.

**The fix is still simple, though**: `HeightOverride` is a normal overridable UMG property, not compiled-in logic — patchable with `SetPropertyValue` exactly like `NumRecords` was. 688 / 8 tiles ≈ 86px/tile, so the new height for N tiles is roughly `86 * N`. No `ScrollBox` injection needed for a modest slot-count increase.

**Mod #1's real shape, now three coordinated pieces**:
1. Patch `LoadoutComponent.Slots[1].NumRecords` upward (already confirmed to work, proxies through `GetMaxRecordsForTemplate` correctly).
2. Hook `Widget_LoadoutsPanel_C:Refresh` to make the tile-creation loop go past its hardcoded clamp of 8 (still needs the exact `CreateWidget`/`AddChild` call shape — next investigation step).
3. Patch `SizeBox_0.HeightOverride` proportionally to the new tile count, so the extra tiles have room to render without overflowing/spilling.

### 3.4j CONFIRMED — `Widget_Loadout_C`'s class variables reveal the tile-creation recipe

FModel property-JSON dump of `Widget_Loadout_C` itself (`Widget_Loadout.json`, repo root — the per-tile widget, singular, distinct from `Widget_LoadoutsPanel.json`). Its class-level (not function-local) variables:

- **`Index`** (`IntProperty`) — `PropertyFlags: Edit | BlueprintVisible | ExposeOnSpawn`. `ExposeOnSpawn` means this is set as a spawn parameter directly on the `CreateWidget` call itself (the "Class Defaults" pins UMG exposes on a Create Widget node when a variable has this flag), not via a separate call after construction.
- **`LoadoutTemplate`** (`ObjectProperty`, `LoadoutTemplate` class) — `PropertyFlags: Edit | BlueprintVisible | DisableEditOnInstance`, no `ExposeOnSpawn`. Set via a plain property write after construction — same `SetPropertyValue` mechanism already used safely for `NumRecords`.
- **`OnClicked`** — `MulticastInlineDelegateProperty`, `BlueprintAssignable`. Bound post-construction (matches the panel's own `K2Node_CreateDelegate_OutputDelegate_1` step seen in `Widget_LoadoutsPanel_C`'s `Refresh`).
- The tile has its **own `Refresh` function** (`Widget_Loadout.json` line ~1513), which reads `Index` + `LoadoutTemplate` + a component reference to build its own display text/icons (uses `Add_IntInt` → `Conv_IntToText` → `Format` — i.e. builds "Loadout N" style label from `Index`). Calling this after setting `Index`/`LoadoutTemplate` should make a manually-created tile self-populate.

**Scope flag for the user**: everything up to this point (`NumRecords`, `HeightOverride` patches) has been simple property writes — the safest, most-proven operation this session. Actually implementing "create extra tiles past the hardcoded clamp" requires constructing a new `Widget_Loadout_C` instance, setting an `ExposeOnSpawn` param, adding it to a live container (`AddChild`), and calling a function on it — meaningfully higher complexity and crash risk than anything done so far (closer to the `SetDisplayNameForLoadout`/`FText` crash territory than the `NumRecords` territory). Should be built and tested incrementally, one small piece at a time, not attempted as a single script.

### 3.4k Tooling notes learned while building the extra-tile logic incrementally

- **`NotifyOnNewObject`'s callback fires at raw construction time**, before the object's own bound widget variables (e.g. a `UserWidget`'s `LoadoutList`) have been initialized. Grabbing `panel.LoadoutList` immediately inside a `NotifyOnNewObject(ClassPath, function(panel) ... end)` callback returned a non-nil but `IsValid() == false` object — too early. Fix: only capture the object reference in `NotifyOnNewObject`, then do the actual work in a `RegisterHook` on that object's own `Refresh` function (or similar), which fires only after the widget has fully initialized itself.
- **`RegisterHook`'s single-callback form is pre/post depending on the path prefix**: per UE4SS docs, if the path starts with `/Script/` (a native/engine function) the single callback is a **pre**-hook (fires before the original runs); for any other path (Blueprint/asset-rooted, like `/Game/...`) the single callback is a **post**-hook (fires after). Confirmed this in practice — our hook on `Widget_LoadoutsPanel_C:Refresh` (a `/Game/...` path) fired after `Refresh` completed, as needed.
- **HAZARD, upgraded from "soft Lua error" to "confirmed native crash" — `RegisterHook`'s `self` parameter is not safe to touch at all.** First attempt: `self:GetFullName()` (a method call) didn't error, just silently returned `nil`, which then crashed a string concat with a catchable Lua runtime error (`attempt to concatenate a nil value`) — the game itself stayed up. Second attempt, after switching to `self.LoadoutList` (a plain property *access*, not a method call, on the theory that indexing would be safer than calling a method): **this crashed the game outright** — `UE4SS.log` just stopped mid-execution, the exact same signature as the earlier `SetDisplayNameForLoadout`/`FText` native crash (not something `pcall` can catch). **Conclusion: do not touch a `RegisterHook` callback's `self`/`Context` parameter at all** — not properties, not methods — at least not for a Blueprint (`/Game/...`-rooted) function hook. Whatever object wrapper UE4SS hands back for `self` in this context is unsafe to dereference in any way tried so far.
  - This ruled out the entire "hook `Refresh`, use `self` to identify the correct instance" approach. **Final working design**: never call `RegisterHook` on `Refresh` at all. Instead, rely solely on the `panel` object handed directly to a `NotifyOnNewObject` callback (proven safe every time this session, no exceptions) and poll for `panel.LoadoutList:IsValid()` becoming true using `LoopAsync(intervalMs, function() ... return true/false end)` (a documented UE4SS Lua global — return `true` to stop looping, `false` to keep polling) instead of relying on a hook to signal "the widget tree is ready now."
  - **ROOT CAUSE FOUND (after the fact, via UE4SS docs research)**: `self`/`Context` in a `RegisterHook` callback is wrapped in a `RemoteUnrealParam`, not handed over as a plain, ready-to-use UObject. Per UE4SS's own docs, hooked-function parameters (including the `self`/"this" pointer) live in the raw per-call argument frame (Unreal's `FFrame`-based parameter-passing for UFunction calls) rather than as a stable, independently-tracked object handle the way a normal `FindAllOf`/`NotifyOnNewObject`-sourced object is. `RemoteUnrealParam` is UE4SS's safety wrapper around that, and **the documented, correct access pattern is `self:get()`** (example from the docs: `local PlayerController = Context:get()`), which does the actual dereference into a normal, safely-indexable Lua object — only after which normal calls like `:GetFullName()` or `:IsValid()` are meant to be used. We never called `:get()` — we touched the raw wrapper directly both times (as a method call, then as a property access), which is exactly the unsafe path the wrapper exists to prevent. Confirmed via [UE4SS RegisterHook docs](https://docs.ue4ss.com/lua-api/global-functions/registerhook.html) and [RemoteUnrealParam docs](https://docs.ue4ss.com/lua-api/classes/remoteunrealparam.html); a related open bug ([UE4SS-RE/RE-UE4SS#933](https://github.com/UE4SS-RE/RE-UE4SS/issues/933), enum values >255 misreading through `:get()`) confirms this is a real, actively-used, occasionally-fiddly part of the API — not an obscure corner.
  - **RESOLVED — `self:get()` confirmed safe in-game (see 3.4q).** A dedicated ZZTestMod safety test (hook on `Widget_Loadout_C`'s mouse-enter bound-event handler, 3 runs) passed completely: `self:get()` returned the real tile instance, and `:IsValid()`, `:GetFullName()`, and a `.Index` property read all worked on the unwrapped object, no crash. - **Observed but not confirmed root-caused: `NotifyOnNewObject` hooks seem to only reliably fire after the first hot-reload of a session.** On a genuinely fresh game launch, opening the Loadouts screen for the first time did not trigger our `NotifyOnNewObject` callback, even though the screen itself rendered normally. Doing one throwaway hot-reload immediately after launch, then reopening the screen, reliably triggered it every time this was tested (3+ occurrences). Practical workaround: always do one hot-reload right after a full relaunch before testing anything that depends on `NotifyOnNewObject`.
- **HAZARD — writing a UMG property directly (e.g. `SizeBox.HeightOverride = X`) doesn't always trigger a re-layout.** The write succeeds (no error, reads back correctly) but has no visible effect, because Slate caches layout state in the underlying native widget and only specific setter *functions* (e.g. `SetHeightOverride(float)`) invalidate that cache as a side effect. **When changing a UMG widget's visual layout property, call the real setter function, not a raw property write** — this is the same class of trap as the earlier `NumRecords`-vs-`GetMaxRecordsForTemplate` distinction, but for layout instead of data.

### 3.4n CONFIRMED — why the manually-constructed tile ignored clicks: `ComponentDelegateBinding` requires the real `CreateWidget` lifecycle

Right-click (save) on the extra tile did nothing, while the hover tooltip worked. Tested calling `newTile:Construct()` manually after `StaticConstructObject` — **no effect**, right-click still dead. Root cause found in the `Widget_Loadout.json` FModel dump: the very first object in the export is a **`ComponentDelegateBinding`** owned by `Widget_Loadout_C` that wires the tile's internal `Button` widget (a `FocusButtonWidget`, part of the tile's own WidgetTree) to the tile's handlers:

- `Button.OnMouseRightClick` → `BndEvt..._0_OnFocusMouseEventDelegate...` (the save action)
- `Button.OnClicked` → `BndEvt..._2_OnAdvButtonClickedEvent...` (the load action)
- `Button.OnMouseEnter` / `Button.OnMouseLeave` → `BndEvt..._4` / `BndEvt..._3`

These "dynamic bindings" are applied by `UUserWidget::Initialize()` — a **native, non-reflected** function (not a UFunction, so not callable from Lua) that `CreateWidget` runs automatically and raw `StaticConstructObject` skips entirely. This cleanly explains the split behavior: the tooltip is a *pull-based* query (`GetValidInputActions` via `BPI_TooltipAction_Interface`, the engine asks the widget) so it worked with no bindings, while clicks are *push-based* delegates that were simply never bound. `Construct()` couldn't fix it because binding happens in `Initialize`, not `Construct`.

**Fix adopted (mirrors the game's own code path)**: construct the tile via `WidgetBlueprintLibrary.Create` — the native static function behind the Blueprint "Create Widget" node, which is literally what `Widget_LoadoutsPanel_C:Refresh`'s `Create` node calls. From Lua: `StaticFindObject("/Script/UMG.Default__WidgetBlueprintLibrary")` then `wbl:Create(panel, tileClass, playerController)` (world-context object, widget class, owning player from `FindFirstOf("PlayerController")`). This runs the full lifecycle: `Initialize` (delegate bindings), and `Construct` fires naturally when the widget enters the tree via `AddChild`. Fallback if this ever breaks: manually replicate the bindings from Lua with `newTile.Button.OnMouseRightClick:Add({ Object = newTile, FunctionName = FName("BndEvt__...") })` — documented but untested.

**Status: tested in-game — partial fix.** The `WidgetBlueprintLibrary.Create` tile renders correctly and the tooltip's RMB indicator now *lights up* on right-click (input reaches the tile's internal button — new behavior vs. `StaticConstructObject`), but the "SAVE LOADOUT?" confirmation dialog still doesn't appear.

### 3.4o CONFIRMED — the save/load dialogs are the PANEL's job; the panel subscribes to each tile's delegates, and nobody subscribed to ours

Traced via the panel's FModel JSON: the tile itself never calls any save function — no save/dialog-related calls anywhere in `Widget_Loadout.json`'s function locals. **Fix attempted and FAILED — hard UE4SS limitation confirmed in-game**: after creating the tile, tried replicating the three bindings from Lua via `newTile.OnClicked:Add({ Object = panel, FunctionName = FName("OnLoadoutClicked") })` etc. Result: `Error: [handle_unreal_property_value] Tried accessing unreal property without a registered handler. Property type 'MulticastInlineDelegateProperty' not supported.` — the installed UE4SS build cannot even *read* a multicast delegate property from Lua (the error fired on the `newTile.OnClicked` index lookup, before `:Add` was ever reached). Two additional lessons from the failure:
- **This error class pierces `pcall`**: despite the access being wrapped in `pcall`, the error aborted the entire enclosing callback — everything after it (tile `Refresh`, `AddChild`, final print) never ran, so the tile silently disappeared from the screen. Treat `[handle_unreal_property_value]` errors as callback-fatal, not catchable.
- The delegate-`:Add` syntax researched earlier evidently applies to a **newer/dev UE4SS** than what's installed — the current dev docs (`docs.ue4ss.com/dev/lua-api/classes/delegateproperty.html`) describe `DelegateProperty` (single-cast, assignable as a plain `{ Object = ..., FunctionName = ... }` table) and a `MulticastDelegateProperty` chapter with `Add`/`Remove`/`Clear`, but the installed build's property-handler registry clearly has no `MulticastInlineDelegateProperty` entry. A 2023 UE4SS discussion (`github.com/UE4SS-RE/RE-UE4SS/discussions/132`) confirms delegate support was a long-open feature request, with suggested workarounds being (a) hook the UFunctions that delegates eventually invoke, or (b) modify the Blueprint asset itself.

### 3.4bb Widget styling from Lua — struct write-back rule, StaticFindObject path format, tooltip action-row injection (all user-confirmed in-game 2026-07-13)

Learned finishing LoadoutNamer's cosmetics (edit-box styling + tooltip "F2 Rename" prompt). All generalize beyond that mod:

- **Struct property writes need read-modify-WRITE-BACK.** Reading a struct property (`box.WidgetStyle`) hands back a detached copy; nested field writes mutate that copy invisibly. - **`StaticFindObject` requires the FULL object path** (`Package.ObjectName`): `/Game/UI/Fonts/GFGRemnantCracked_Font.GFGRemnantCracked_Font` works; the bare package path fails with `GetPackageNameFromLongName: Name wasn't long`.
- **H4 re-confirmed on a layout property**: raw-writing `TextBlock.MinDesiredWidth` changes nothing on screen; the real `SetMinDesiredWidth()` setter works immediately. Raw writes are only for plain data, never anything Slate has to react to.
- **Fonts**: `FEditableTextBoxStyle` exposes the font at `WidgetStyle.TextStyle.Font` on this build (`.Font` directly does not exist); `FSlateFontInfo.Size` and `.FontObject` are writable. `UTextBlock.Font` same treatment via write-back.

### 3.4dd CONFIRMED — mod enable/disable: `enabled.txt` overrides everything; `mods.txt` is the only registry that matters; hand edits to `mods.json` are discarded

Found 2026-07-12 while trying to launch mod-free: setting both registry files to disabled did nothing — the mods still loaded.

- **`enabled.txt` (mere presence, contents irrelevant) force-enables a mod, bypassing the registry entirely.** It exists as UE4SS's zero-config drop-in path for end users. Since this project registers every mod in `mods.txt` anyway, the files were redundant and harmful — **removed from all mod folders 2026-07-12** (registry-only loading confirmed working by a clean launch). Don't add them to new mod folders.
- **`mods.txt` is the sole effective registry in current builds.** `mods.json` is the planned future replacement ([UE4SS PR #540](https://github.com/UE4SS-RE/RE-UE4SS/pull/540)), but during the transition `mods.txt` takes precedence and UE4SS *overwrites* `mods.json` from `mods.txt` at launch — user-confirmed empirically: disabling via `mods.txt` worked, disabling via `mods.json` was silently reverted. Register new mods in `mods.txt` only; never hand-edit `mods.json`. Precedence is slated to flip in some future UE4SS release — if registry edits ever stop working after a UE4SS upgrade, re-check which file wins.
- Enable/disable changes take effect on a full relaunch (hot-reload restarts already-enabled mods; it doesn't re-read enable state).

### 3.4v ScrollBox injection WORKS — runtime reparenting of live UMG widgets is viable

To fit more tiles than the panel's fixed height allows (the vanilla tree is `SizeBox_0` with a hard `HeightOverride=688` → `LoadoutList` VerticalBox, no scrolling anywhere), we splice a runtime-created engine `ScrollBox` between them: `SizeBox_0 → ScrollBox → LoadoutList`. **User-confirmed fully working on first attempt**: tiles render at normal size, mouse wheel scrolls, overflowed tiles are reachable, tooltips and all click/key interactions work on scrolled-to tiles.

Key points:
- **`StaticConstructObject` is fine for engine widgets.** `ScrollBox` is a raw C++ widget (`/Script/UMG.ScrollBox`), not a Blueprint UserWidget — it has no `Initialize()`-time `ComponentDelegateBinding` step to miss, which is exactly what made raw construction fail for the tile widget (3.4n). Constructed with outer = `panel.WidgetTree`.
- **Reparenting recipe** (game thread): grab `sizeBox = list.Slot.Parent` **before** detaching (after `RemoveChild`, `list.Slot` is gone), then `sizeBox:RemoveChild(list)` → `sizeBox:AddChild(scrollBox)` → `scrollBox:AddChild(list)`. All three worked live, mid-screen-display, with no visual glitch.
- **Desired-size sizing worked out**: inside a ScrollBox, children get their desired size instead of fill space — the concern that tiles might collapse to zero height did not materialize; tiles keep their native ~86px.
- The SizeBox stays at its native 688 (no more `SetHeightOverride` growth). NOTE: `list.Slot.Parent` now resolves to the **ScrollBox**, not the SizeBox — any future code reaching for the SizeBox must go one level further up.
- Two benign log artifacts each session: panel instances constructed during class-load / world transition never get a valid `LoadoutList` and time out the 40-attempt poll — these are not player-facing screens; the real screen-opens proceed normally.

**Vanilla scrollbar reuse:** the stats scrollbar's design template is `/Game/UI2/UI_Widgets/UI_Game/UI_Game_Equipment/Widget_AdvancedStats.Widget_AdvancedStats_C:WidgetTree.ScrollBox_143` (confirmed in the object dump and UMG headers). UE4SS 3.0.1 supports it as argument 8: `StaticConstructObject(scrollClass, tree, 0, 0, 0, false, false, template)`. This inherits the native styling and scrolling settings without Lua struct write-back. The template lacks `RF_ArchetypeObject`; leave `AssumeTemplateIsArchetype` false. Copied slot/content references are shared, so do not use `ClearChildren` callbacks on them. Before Slate construction, `vanilla_scrollbox.lua` verifies distinct array containers and backing buffers, empties only the new widget's private `Slots` array, and checks the source allocation, child identities and order remain unchanged. Missing/unsafe templates produce an explicit engine-default fallback. Mock tests cover the constructor contract and source safety. Appearance was user-confirmed in the stable-compatible live test build, and its log confirms the native-template path rather than fallback.

### 3.4b HAZARD — calling a UFunction with an FText parameter via Lua crashed the game

Attempted `comp:SetDisplayNameForLoadout(slot.Template, 0, "ZZTestMod Custom Name")` (calling the confirmed-real `LoadoutComponent:SetDisplayNameForLoadout` function via Lua reflection, passing a plain Lua string for the `NewDisplayName` FText parameter) inside a `pcall`. **Result: hard game crash**, not a caught Lua error. `UE4SS.log` shows the last successful line was the property read just before this call — nothing was logged from inside or after the call, confirming the crash happened synchronously during the function invocation itself.

**Key lesson**: `pcall` only catches Lua-level errors. It does **not** protect against a native engine crash (e.g. bad memory access inside a C++/Blueprint-native function called via reflection) — those bypass Lua's error handling entirely and take the whole process down. This is a meaningfully different risk profile than the property reads/writes done so far (`comp.Slots`, `slot.NumRecords = 20`), which have all worked safely — **calling functions via Lua reflection, especially ones taking non-trivial parameter types like `FText`, is higher-risk than reading/writing properties directly**, and should be tested more cautiously (e.g. try a read-only function like `GetDisplayNameForLoadout` first, confirm calling functions on this class works at all, before attempting a write/mutating call).

**RESOLVED via web research** (UE4SS's own docs/GitHub issues, `docs.ue4ss.com/lua-api/global-functions/ftext.html` + `UE4SS-RE/RE-UE4SS` GitHub issues): this is a known UE4SS Lua issue, not specific to this mod or Remnant 2. Passing a plain Lua string directly where a function parameter expects `FText` causes UE4SS to misplace arguments on the call stack and attempt to write to the property through a null pointer — a hard native crash, exactly matching what we saw. **Fix**: UE4SS exposes a global `FText()` constructor in Lua specifically for this — wrap the string first:

```lua
local text = FText("My String")   -- correct
comp:SomeFunctionExpectingFText(text)

-- NOT this (crashes):
comp:SomeFunctionExpectingFText("My String")
```

Confirmed the read-only `GetDisplayNameForLoadout` call (object + int params only, no FText involved) works fine via direct Lua call — the crash really was isolated to the raw-string-into-FText-parameter case. Next retry of `SetDisplayNameForLoadout` should wrap the new name in `FText(...)` before passing it.

### 3.5 Live View GUI limitation (tooling note)

The UE4SS Live View / Object Explorer GUI, when you click into a property node under an object's `Class` branch, shows only **FProperty reflection metadata** (`ArrayDim`, `ElementSize`, `PropertyFlags`, `OffsetInternal`, etc.) — not the actual current value stored on a live instance. For reading real runtime values (array contents, current ints/strings/etc. on a specific live object), the reliable method confirmed working is: write a small Lua snippet (e.g. temporarily added to `ZZTestMod`) using `FindAllOf("<ClassName>")` to grab live instances, then read/print their properties directly, checked via `UE4SS.log`. Prefer this over screenshotting the Live View property panel — it won't have real values.

### 3.6c MOD #3 SHIPPED (2026-07-14) — EquipmentSearch final architecture, item-text data model, and three new hazards

`EquipmentSearch/Scripts/main.lua` is done and user-verified in-game ("grey health" → 10 correct rings; 0 name-only items across all 213 rings). Supersedes 3.6b's *planned* hybrid: **`ShouldHideItem` + `RefreshInventory` was NOT used.** Every vanilla rebuild entry point early-outs when the game thinks nothing changed, so the shipped architecture is direct visibility toggling instead:

- **Architecture**: unhide the game's bar per list construction (`NotifyOnNewObject` + readiness poll, 3.6b's two hiding layers), collapse the vestigial combo box; hook the bar's `TextChanged` + X-button events; on query change walk `list.InventoryGrid`'s card children and `SetVisibility(Collapsed/restored)` per match (Collapsed reflows the WrapBox so matches flow together; original visibility recorded per card and restored exactly). Multiple list instances coexist (equipment screen + Inventory-tab materials/quest/usable lists) — tracked per list full name, each synced against its *own* text box. Post-hooks on `Update Inventory List` / `Build Inventory List` plus a 300 ms watchdog (a full re-apply pass measured ~2 ms) re-assert the filter after vanilla rebuild paths, some of which bypass both hooks.
- **Item text per ItemID** comes from each card's `Get_InspectInfo({})` (BlueprintPure; out-struct fields spread into the passed Lua table). Cached per session, built lazily from each list's own grid children (never the global card pool — stale pooled cards poisoned the cache once).
- **The effect-text data model (the hard-won part)**: `InspectInfo.Description` = lore paragraph and `FlavorText` = lore quote (both deliberately excluded — search is gameplay-only, user decision). Real effect text lives in the arrays, in TWO different places by item style: stat-style items → `Mods[].Label` (`InspectMod`); trigger-style items (~30 rings, e.g. Disaster Converter, Offering Stone) → `Stats[].CustomDescription`, a field **inherited from `InspectStatBase`**. Some items' `Mods[].Label` merely echoes the item name (Momentum Driver) — effect detection must be echo-aware. Array entries arrive as `LocalUnrealParam` wrappers needing `:get()` (out-param arrays = Lua tables; arrays read off returned structs = TArray userdata).
- **HAZARD (H9) — per-struct field safety**: reading a field name on a struct that doesn't own it is a **native crash** (pcall useless). Stats entries (`InspectStat`) and Mods entries (`InspectMod`) have different fields; a shared reflected field list crashed the full cache pass by trying Stats' `CustomDescription` on Mods entries, while a Stats-only sweep of all 213 rings was clean (probe P8). Resolve field lists **per array property**, never shared.
- **HAZARD (H10) — `ForEachProperty` does not walk super-structs.** `InspectStat` shows only its own 3 fields; `Label`/`CustomDescription`/etc. live on `InspectStatBase` and are silently missing. Walk the `GetSuperStruct()` chain (probe P6/P7).
- **HAZARD (H11) — zero-filled FText in synthesized struct params.** Passing an empty Lua table as a struct ref/out param "works" (call succeeds, keys enumerable) but UE4SS zero-fills it, and `ToString()` on a zero-filled FText dereferences null → native crash (probe P5 round A pinpointed this exactly). Only call `ToString()` on FTexts the *game* populated.
- **Dead ends, proven**: re-invoking the game's inspect pipeline to regenerate trigger-ring text — `cdo:ModifyInspectInfo(...)` with a REAL populated info struct executes without crash but changes nothing (P5 round B); `Widget_ItemTooltip_C:GetInspectInfo` hook registers but never fires on inventory hover (P6). Neither is needed given the `CustomDescription` finding.
- **Debug commands** (typed into the search bar, kept in the shipped mod): `!<word>` dumps full cached text of matches, `!!` clears the cache, `!?` lists name-only items (the after-a-game-patch health check; 0 as of 2026-07-14).
- **Tab-hotkey suppression while typing** (user-confirmed 2026-07-14): T/I/M no longer yank the menu mid-word. Same mechanism as LoadoutNamer (§3.4aa — tab switches early-out when the tab *button* is Hidden; visibility 2 keeps layout space), but the session boundary is new: `Widget_InventorySearchFilter_C` overrides **`OnAddedToFocusPath` / `OnRemovedFromFocusPath`** (dump ~1705) which fire when keyboard focus enters/leaves the search box — hookable with `RegisterHook`, and suppression engages on click-in *before* the first keystroke (no race). Restore on focus-out; a leaked Hidden state self-heals on menu reopen. Generalizable: any "while this widget has focus" behavior can hook these UserWidget overrides when the BP implements them.
- **Known accepted limitations**: upgraded items keep their old "+N" label in the cache until relaunch (name still matches); Inventory-tab lists don't persist the filter across tab switches.

### 3.7 Stable UE4SS + AllowModsMod compatibility investigation (2026-07-14) — three capability gaps found and gated

Trigger: most Remnant 2 modders run `AllowModsMod`/AAM for asset/pak mods, which requires stable UE4SS (its bundled C++ `main.dll` crashes UE4SS boot against `experimental-latest`'s ABI — the reason we're on experimental at all, §3.4u). Investigated whether the three shipped mods could also run on stable UE4SS instead of requiring users to disable AllowModsMod.

**AllowModsMod itself is a moving target, unrelated to our code.** A mid-2026 Remnant 2 patch broke AllowModsMod independently (community-confirmed: crashes on boot, fixed by a subsequent AAM update). Its Nexus "latest" download's own bundled `UE4SS.log` is dated 2024-09-28, so "latest AAM" does not mean "latest UE4SS" — chasing an exact AAM+UE4SS version combination is not a fixed target. Directly observed in our own testing (both against the 2024 project backup and against that Nexus download's bundled files, run separately): `[AllowModsMod]: Delegate not found. Unable to patch.` — it never fully initializes against the current game version in either case, independent of anything in this project. None of this is required to answer the question that actually matters: **does our own code degrade safely on any UE4SS build that lacks a capability, instead of crashing?**

**Three UE4SS Lua capabilities our shipped code depended on turned out to be experimental-only**, confirmed by testing against the plain stable v3.0.1 Beta backup (`Win64\_ue4ss-3.0.1-backup`, no AllowModsMod needed to isolate the variable):

1. **Multicast delegate property access** (MoreLoadoutSlots, `tile.OnClicked` etc.) — merely *reading* a `MulticastInlineDelegateProperty` throws `Property type 'MulticastInlineDelegateProperty' not supported` on stable.
2. **Struct property write-back** (LoadoutNamer, `label.Font = f` / `box.WidgetStyle = style`) — assigning a Lua-mutated struct copy back onto a property throws `push_structproperty::lua_to_memory: StructData as userdata is not yet implemented` on stable.
3. **`InspectObject` property resolution on Stats/Mods struct entries** (EquipmentSearch, `extractTexts`'s belt-and-braces fallback) — throws `Was unable to retrieve property 'InspectObject' mapped to 'ScriptStruct ...InspectStat'` on stable.

**Critical shared behavior: all three errors pierce `pcall` at every nesting level** — not a catchable Lua error, it aborts the entire enclosing function (and, if not caught by whatever UE4SS-level boundary invoked it, the whole native callback for that tick). This means the existing pattern of "wrap the risky call in `pcall`, check the boolean" does **not** protect against these — the abort happens regardless of `pcall`, and any code positioned before the risky line in the *same* function silently never runs on future retries.

**The fix pattern used (applied in all three mods)**: a one-time capability probe.
- Two module-level flags: `xProbed` and `xSupported` (both start `false`).
- Set `xProbed = true` as a plain assignment **immediately before** the risky line — this is a normal Lua statement, so it survives even if everything after it in the same function aborts.
- Set `xSupported = true` **immediately after** the risky line, inside the same `pcall` — this is only reached if the risky line didn't abort.
- Every call site checks `if xProbed and not xSupported then skip end` before attempting the risky operation again.
- Net effect: the very first attempt in a session may abort its enclosing function harmlessly (one engine-level error line, not a flood), but every subsequent attempt skips the risky path cleanly and the surrounding code completes normally from then on.

**Ordering matters for widgets that need pre-`AddChild` styling.** Slate bakes initial layout from whatever properties are already set at `AddChild` time (documented previously for `styleEditBox`, §3.4bb) — styling must still happen *before* `AddChild`, even with the probe pattern. Moving it *after* `AddChild` (tried first, then reverted) fixes the abort but silently breaks the visual styling on builds where it *does* work, since Slate already built the widget with default values by the time the property gets set.

**Confirmed working after the fix (stable v3.0.1 Beta, no AllowModsMod)**: no crash for the full session. MoreLoadoutSlots' hook-forwarding fallback (its original pre-experimental mechanism, §3.4o) creates all 20 tiles and user-confirmed saving works on one of the extra slots; load/equip/delete via the fallback weren't separately retested this session, but route through the same pre-existing mechanism (not new code). EquipmentSearch filters correctly (verified: typing narrowed results as expected). LoadoutNamer's rename flow (open box, type, save, cancel) works end-to-end, just with unstyled (engine-default) prompt/edit-box appearance.

**Known accepted limitation, stable-only, not from today's fix**: the pre-existing first-launch `NotifyOnNewObject` quirk (§3.4k/3.4t, the reason we upgraded to experimental in the first place) still reproduces on stable — the very first screen-open of the relevant menu after a cold launch gets no mod behavior (no extra loadout tiles, no name/hover binding, no search bar); closing and reopening the screen once fixes it for the rest of the session. A hot-reload (Ctrl+R) also works as a one-time per-launch workaround. This is unrelated to and not fixed by the capability-gating work above. **User-confirmed 2026-07-17: reproduces identically in all three shipped mods** (MoreLoadoutSlots, LoadoutNamer, EquipmentSearch) — expected, since all three share the same `NotifyOnNewObject`-based construction-time bootstrap, but this is the first session it was verified per-mod rather than assumed from the mechanism. Documented independently in each mod's `*_DONE.md` "Known accepted limitations" section (no code fix exists for any of them).

**Known accepted limitation, stable-only, discovered but not chased further (user decision 2026-07-14)**: LoadoutNamer's tooltip rename-prompt occasionally logs `'F2 Rename' prompt added` many times in the same instant (observed: 11x for one hover). Not a crash, not user-visible (only the currently-displayed tooltip instance matters), and not caused by today's fix — stable UE4SS's `FCallbackGarbageCollector` appears to clean up destroyed tooltip widget instances less promptly than experimental's, so `FindAllOf(TOOLTIP_CLASS_NAME)` transiently returns multiple still-`IsValid()` stale instances, each independently triggering prompt creation. Wasted work and log noise only.

**Bottom line**: with the capability-gating fix, all three mods are now safe to run on stable UE4SS (no crash, functional degradation only), making stable+AllowModsMod support a real option again if wanted — subject to the two accepted quirks above and AllowModsMod's own independent compatibility churn.

### 3.8 First-launch `NotifyOnNewObject` quirk (§3.4k/3.4t/3.7) — likely root cause identified via UE4SS upstream history, no fix on stable yet

Web research (2026-07-17) into why this quirk reproduces on stable but not experimental, and whether an upstream or Lua-side fix exists.

**Likely root cause: UE4SS PR [#1134](https://github.com/UE4SS-RE/RE-UE4SS/pull/1134)** (`feat(Lua): NotifyOnNewObject for unloaded classes`, merged 2026-02-18). Before this fix, registering `NotifyOnNewObject` for a class that hadn't loaded yet meant the callback **never fired**, even on that class's first real instantiation later — the author's own test case (a Palworld UI widget absent at the main menu, loading only later) is structurally identical to our situation: the Loadouts/Inventory panel classes aren't loaded at mod-init, only when the player actually opens that screen for the first time.

**Version timeline that explains the stable/experimental split**:
- Stable tag `v3.0.1` released 2025-02-14 — a full year before the fix. This is the version AllowModsMod's bundled `main.dll` requires (AAM's own Nexus bundle ships a UE4SS.log dated 2024-09-28, even older).
- No newer stable tag exists as of this research (`v3.0.1` is still the latest official tagged release on the GitHub releases page) — the fix was never backported into a stable release.
- `experimental-latest` is a rolling build and picked up PR #1134 automatically, consistent with the quirk disappearing when we upgraded (§3.4u) without doing anything targeted at it.

**Caveat — not a 100% confirmed match.** §3.4t's disproof test registered a *second*, late `NotifyOnNewObject` callback *after* the target class had already loaded, and even that didn't fire when the screen subsequently opened. PR #1134 fixes the *original early* registration (made before the class loads) never being retroactively matched once it does load — a related but distinct failure mode from what 3.4t tested. So this is the strongest lead found, not a verified-to-the-line root cause.

**Options evaluated, in order of cost**:
1. **Current workaround** (already shipped in all three mods' `*_DONE.md` docs) — close/reopen the screen once, or one Ctrl+R hot-reload, self-heals for the rest of the session. Zero engineering cost.
2. **Lua-side self-healing poll (not yet implemented)** — `FindAllOf` doesn't depend on `NotifyOnNewObject` at all. A lightweight periodic `FindAllOf(panelClassName)` scan (e.g. via `LoopAsync`, started at mod init as a backstop alongside the existing `NotifyOnNewObject` registration) could catch an already-alive panel instance shortly after the screen opens even when the notify never fires — turning "broken until the user manually reopens" into "self-corrects within ~1-2s, no user action needed." Not prescribed anywhere in UE4SS docs; an idea consistent with patterns already used in these mods (readiness polling), untested.
3. **Swap in a newer official stable UE4SS tag** — doesn't help; no stable tag postdates the fix.
4. **Get AllowModsMod compatible with experimental UE4SS** — the actual reason stable is needed at all; AAM's `main.dll` is ABI-bound to old UE4SS and crashes on experimental (§3.4u). Outside our control — depends on an AAM update or a rebuilt equivalent.

**Not pursued yet**: option 2 (poll backstop) is the only one worth prototyping; next step would be a ZZTestMod probe on the stable backup to see if a `FindAllOf` backstop actually closes the gap in practice.

Sources: [PR #1134](https://github.com/UE4SS-RE/RE-UE4SS/pull/1134), [RE-UE4SS Releases](https://github.com/UE4SS-RE/RE-UE4SS/releases), [NotifyOnNewObject docs](https://docs.ue4ss.com/lua-api/global-functions/notifyonnewobject.html), [FindAllOf docs](https://docs.ue4ss.com/lua-api/global-functions/findallof.html).

### 3.9 Stable-UE4SS styling gap (§3.7 point 2) — alternatives investigated, none pursued (user decision 2026-07-17)

Web research into whether LoadoutNamer's rename-prompt/edit-box styling (currently unstyled-engine-default on stable, §3.7) could be recovered without waiting on upstream UE4SS.

**No upstream fix is coming, and it wouldn't help even if it did.** Confirmed via GitHub: the struct write-back support (`push_structproperty`) that stable lacks landed only in `experimental-latest`, never backported to a numbered stable tag — `v3.0.1` (2025-02-14) is still the latest official stable release, and the [release-cycle discussion (#498)](https://github.com/UE4SS-RE/RE-UE4SS/discussions/498) shows no roadmap for a new one; releases happen when a maintainer finds time, not on a schedule. Moot anyway: AllowModsMod's bundled `main.dll` is ABI-locked to the old stable build (§3.7 point 4), so a hypothetical new stable UE4SS.dll wouldn't be usable with AAM without an AAM update of its own — outside our control either way.

**Two alternatives were identified but not attempted (user call: not worth blocking the release over cosmetics-only degradation)**:

1. **Bypass the struct copy-and-writeback via raw memory pointers.** The failing call (`push_structproperty::lua_to_memory`) only fires when converting a *Lua-side struct value* into an object's memory (assignment or function-argument passing) — exactly what `box.WidgetStyle = style` does. UE4SS's `Property` class separately exposes `ContainerPtrToValuePtr(Container, ArrayIndex) → LightUserdata`, and `UScriptStruct` exposes `GetStructAddress()`/`IsMappedToObject()`/`IsMappedToProperty()` — plausibly the machinery for a *live, memory-mapped* struct value (as opposed to the detached copy `obj.WidgetStyle` currently returns, which is why the whole-struct writeback was needed at all). If obtainable, nested leaf writes (`.Font.Size`, `.FontObject`, color channels) are all scalar-typed (float/object) with their own already-working marshaling code, never touching the broken struct path. **Not confirmed** — documentation doesn't show the exact construction step, and this API may have been added in the same body of work as general struct support, making it equally likely to be absent on old stable. Would need a ZZTestMod probe against the stable backup to know for sure (cheap to test, ~30-60 min; outcome genuinely uncertain).
2. **Stop building the styled widgets ourselves — reuse an existing pre-styled game asset instead**, the same trick that makes EquipmentSearch's search bar work at all (unhiding `Widget_InventorySearchFilter`, a widget the game already shipped pre-styled, rather than building one from scratch). If the game has any existing small, dark, in-line text-input Blueprint elsewhere in its UI, constructing off *that* class instead of the bare engine `/Script/UMG.EditableTextBox` would inherit correct styling for free via normal UObject CDO-copy semantics — no runtime struct write needed, works identically on any UE4SS build. Requires an FModel dev-data pass through the game's UI assets to see if a suitable candidate exists; not guaranteed to find one. Low implementation effort if found, dead end if not.

### 3.10 MOD #4 IDEA (Collection Tracker) — Phase 0 research spike: confirmed no persistent "ever obtained" flag exists

New mod idea: a spreadsheet-style screen showing every unique equippable item (armor, amulets, rings, weapons, weapon mods, archetypes, mutators, traits, certain consumables) and whether the player has obtained it. Before any UI/architecture work, the open question was whether ownership can be tracked persistently (surviving sell/dismantle) or only via current inventory contents (EquipmentSearch's existing read pattern only sees current contents).

**Dead end, confirmed structurally (2026-07-27) — the game has no persistent discovery/collection-log data anywhere in native reflection.**

- FModel export of `/Game/_Core/Achievements/` (`dev-data/Exports/Remnant2/Content/_Core/Achievements/`) shows `Achievement_Armor_Set` is a per-set struct (3 `SoftClassProperty` slots for head/body/legs BP class refs), used only by `Character_Master_Player_Base_C`'s `Get Armor Sets Acquired` Blueprint function to drive a Steam-achievement counter ("Acquire 10 Melee Weapons", "Choose Your First Archetype" per `Achievement_Strings.json`) — not a browsable catalog, and not per-piece.
- That function's locals reference `HasItem` (a native call) to check ownership per set piece — this was the lead investigated for a possible "ever owned" check.
- **UE4SS's "Dump CXX Headers" dumper** (Dumpers tab in the debug GUI, F10/Tilde) produced real typed C++ declarations under `ue4ss/CXXHeaderDump/` (one `.hpp` per native *package*, not per class — e.g. all of `/Script/Remnant` is in `Remnant.hpp`, all of `/Script/GunfireRuntime` in `GunfireRuntime.hpp`). This is the tool flagged back in §2/dev-setup as "useful once generated" but never actually run until now — confirmed genuinely useful, worth reaching for earlier next time a native function signature is needed instead of guessing via trial calls.
- Confirmed signature (`GunfireRuntime.hpp`): `bool UInventoryComponent::HasItem(TSoftClassPtr<AItem> ItemBP, int32 Quantity, int32 ItemLevel)` — base class of `RemnantPlayerInventoryComponent`. 3 params + implicit bool return matched the "UFunction expected 4 parameters" error surfaced by a blind zero-arg call attempt (round 2 probe, ZZTestMod).
- Same class exposes `TArray<FInventoryItem> Items` as a plain property — the actual live inventory. `HasItem` is almost certainly just a filtered check against this same array (Quantity/ItemLevel are live-state filters, not history lookups).
- `FInventoryItem` fields: `ID`, `ItemBP`, `New`, `Favorited`, `Hidden`, `EquipmentSlotIndex`, `InstanceData`, `EquippedActor` — no discovered/ever-obtained bool.
- Grepped the entire `/Script/Remnant` package dump (`Remnant.hpp`, 229KB) for `Discover`, `Journal`, `Codex`, `Compendium` — **zero matches**. `GunfireSaveSystem.hpp` (the save-system module) has none either.

**Conclusion (user-confirmed, proceeding anyway 2026-07-27)**: Collection Tracker can only reflect current inventory contents, same ceiling as EquipmentSearch. A sold/dismantled unique will show as "missing" again — this is a permanent, structural limitation, not a solvable research gap. `HasItem(class, 1, 0)` is still a useful building block for Phase 1 (rings/amulets proof of concept) — a single reflected ownership check by item class, simpler than EquipmentSearch's grid-walking — but its `Quantity`/`ItemLevel` filter semantics (exact match vs. minimum/"any") aren't yet verified in-game.

**HAZARD (native crash, confirmed 2026-07-27)** — calling `HasItem(ItemBP, Quantity, ItemLevel)` from Lua with a raw `UClass` value for `ItemBP` crashed the game (log stopped mid-probe, no Lua error — pcall could not catch it, matching the general FText/struct-marshaling hazard pattern already documented in §3.4b). Root cause: `TSoftClassPtr<AItem>` is **not** a raw pointer like `TSubclassOf<T>` — it's itself a struct wrapping `FSoftObjectPath`. Passing a plain `UClass` there is the same class of mistake as passing an unwrapped string where `FText`/`FName` is required (§3.4b) — it was misclassified as a safe pointer-passing case before testing; it is not. **Do not call `HasItem` (or any other function taking `TSoftClassPtr`) from Lua without first establishing how to construct that soft-pointer struct correctly** (likely needs an `FSoftObjectPath`/`FSoftClassPath`-equivalent wrapper the way `FText()`/`FName()` are required elsewhere — not yet researched). **Superseded by a simpler, zero-risk alternative**: `RemnantPlayerInventoryComponent.Items` (a plain `TArray<FInventoryItem>` property) is directly readable with no function call at all — each entry's `.ItemBP` is a real `TSubclassOf`-style class reference safe to read and compare. Collection Tracker's ownership check should scan this array directly ("does `Items` contain an entry whose `ItemBP` matches item X") instead of calling `HasItem`.

**Lookup-ladder note**: `TrivialObject` hazard — `FindAllOf`-sourced live component instances in this UE4SS build support `IsValid()`/`GetFullName()`/`GetOuter()`/`GetClass()` and direct named-field indexing (`comp.SomeRealPropertyName`), but **not** `ForEachProperty()` or `GetFunction()` (both error "attempt to call a TrivialObject value"). `StaticFindObject`-sourced struct objects (EquipmentSearch's `InspectInfo` pattern) *do* support `ForEachProperty()` — a different code path. Also: indexing *any* field name on one of these live component objects (real or made up) always returns non-nil `userdata` — existence can't be tested by indexing alone; only an actual call (wrapped in `pcall`, args never struct-typed) distinguishes a real bound function (distinctive `UFunction::setup_metamethods` argument-count error) from a nonexistent one (generic `TrivialObject` call error). `StaticFindObject("ClassPath:FunctionName")` does **not** resolve native UFunctions this way either — that path syntax is specific to `RegisterHook`.

### 3.11 MOD #4 named InventoryTracker — Phase 1 (rings/amulets) proven end-to-end, 2026-07-27

Mod folder created (`InventoryTracker/`), registered in `mods.txt`, symlinked. Full pipeline built and user-confirmed working in-game the same session.

**FModel export gotcha that cost most of this session**: the user's first Rings/Amulets export (per-world `Items/Trinkets/...` folders) came from **pakchunk0**, which turned out to contain almost none of the base-game (`World_Base`/`Fae`/`Jungle`/`Labyrinth`/`Nerud`/`Root`) trinkets — only 1-2 items per base world, DLC1-3 fully present. It *looked* like those folders were simply near-empty in the game's data (plausible enough that Phase 1 nearly shipped against a ~130-item list). Re-exporting the same folders from **pakchunk1** revealed the real, full `Items/Trinkets/Rings`+`Amulets` folders for every base world. **Lesson for next categories (armor/weapons/mods/etc.): if a World_* folder's item count looks suspiciously low compared to known totals, check other pakchunks before concluding the content isn't there** — this is a second instance of the project's "beware false negatives" pattern (CLAUDE.md), this time at the asset-export layer rather than the runtime layer.

**Master list build process** (reusable for future categories, originally built in PowerShell as `dev-data/match_items.ps1`, ported to Python in `scripts/InventoryTracker/match_rings_amulets.py` on 2026-07-27 — see the tooling note at the end of §3.12 for why) —
1. Recursively grep every exported `Ring_*.json`/`Amulet_*.json` (excluding `_Inspect`/support-asset files) for its `"Package"` field — the exact, patch-safe asset path.
2. Dedup per item folder (companion files like `_Inspect`/`_Action`/`_Aura`/`_Shield` variants aren't separate items; canonical = shortest `Package` string in the folder).
3. Normalize (strip non-alphanumerics, lowercase) both the asset's folder name and its file basename, and match against a wiki name list (`remnant2.wiki.gg`'s `List_of_rings`/`List_of_amulets`, saved as `dev-data/ring_names.txt`/`amulet_names.txt`) similarly normalized. Try folder-name match first, fall back to file-basename match (several items were renamed during dev — the file's own name sometimes still matches the shipped name even when its containing folder wasn't renamed, e.g. `ConductivePadding/Amulet_ShockDevice.json` → wiki "Shock Device").
4. A short `$manualFixes` hashtable in the script covers the remainder — dev-internal names that differ from the shipped name in a way normalization can't bridge (synonym/reword, e.g. `RingOfTheAdmiral` → "Worn Admiral's Ring", `DowngradedRing` → "Embrace of Sha'Hala"). Every entry here should be either self-evident or user-confirmed in-game before trusting it — **wrong manual pairings are worse than an omission**, since they'd silently show the wrong name for a real, owned item.
5. Final coverage: **328/328 wiki-listed rings+amulets matched** (103/103 amulets, 225/225 rings). One exported asset (`Amulet_BlessedNecklace`, `World_Base`) has no wiki match at all and was left out — user researched it and found "Blessed Necklace" is an item from the original *Remnant: From the Ashes*, not Remnant 2; likely a leftover/misimported dev asset from when content was ported between the two games, not a real obtainable item. Good example of a `[Ring|Amulet]_*.json` existing that isn't actually a real, in-game item — don't assume every exported asset file is player-facing.

**PowerShell gotcha hit twice this session, worth remembering**: `Where-Object` collapses a single-match result to a bare scalar object (not a 1-element array) in Windows PowerShell 5.1. `$scalar.Count` on that is `$null`, and `$null -ge 1` evaluates `$false` — silently treating every single-match case as "no match" with no error. Always wrap `Where-Object` results intended for count-checking in `@(...)` to force array context.

**Ownership check, confirmed correct**: scan `RemnantPlayerInventoryComponent.Items` (plain property read) for an entry whose `.ItemBP` class path (from `GetFullName()`, parsed down to the `/Game/...` portion) matches a master-list `classPath`. Zero reflected function calls — avoids the `HasItem`/`TSoftClassPtr` crash hazard entirely (§3.10). **User-verified in-game**: 302/323 owned on a long-playtime save (93% — plausible for that save, not a red flag), spot-checked both directions (`[ ]` entries confirmed genuinely not owned, obscure `[X]` entries confirmed actually owned) — no false positives/negatives found. Pipeline (FModel export → name matching → live ownership scan) considered proven for rings/amulets.

**Ceiling reminder (from §3.10, still applies)**: this only reflects current inventory contents. No persistent "ever obtained" tracking exists anywhere in the game's data — a sold/dismantled unique will show as missing again. Accepted, documented limitation, not a bug to chase.

**Next steps (not started)**: Phase 2 — generalize to armor/weapons/weapon mods using the same `match_items.ps1` pattern (export the relevant `Items/<Category>/` folders across all `World_*`, check both pakchunks up front this time). Archetypes/traits/consumables will need different logic per §3.10 (they're not one-time-discoverable uniques in the same sense). UI is still just F8 → `UE4SS.log` — no in-game screen built yet; that's the next architecture decision once category coverage is further along.

**Weapon Mods — clean split, worth knowing for any future weapon-related work**: the wiki's "weapon mods" category is actually two structurally different things bundled under one name. The **36 "swappable" mods** (`Items/Mods/<Name>/Mod_<Name>.json`, one file per mod, standalone) are separately owned/tradeable inventory items — this is what `MASTER_LIST`'s `Mod` category tracks. A separate, equally-sized set of **36 "attached" signature mods** (`Items/Weapons/<Weapon>/Mod/Mod_<Name>.json`, permanently baked into specific Special/Archetype weapons — e.g. `Mod_Mortar` on Corrupted Meridian) are NOT separately swappable; owning one is really just "do you own that weapon." **FModel export gotcha, round 2 — this time it went the other way**: Phase 1's lesson was "pakchunk0 can be a stale subset of pakchunk1." Phase 2 needed backfill from **both** directions — 4 weapon mods (`ConcussiveShot`/`HealingShot`/`HotShot`/`ScrapShot`) and roughly two-thirds of the 36 armor sets turned out to live in **pakchunk0** while the rest lived in pakchunk1, i.e. neither pakchunk is reliably "the complete one" — coverage has to be checked per-category, not assumed from a prior category's result. **Overwrite hazard**: FModel exports always write to the same `Content/...`-relative output path regardless of source pakchunk, so blindly re-exporting a whole folder tree from the "other" pakchunk can silently overwrite already-good content with an inferior duplicate at the same path if both paks happen to contain that path. UI is still the next real architecture decision, deliberately deferred again this phase.

**Tooling rewrite, same session (2026-07-27) — PowerShell → Python for the whole matching pipeline**: splicing the Phase 2 entries into `main.lua` via PowerShell (`Set-Content -Encoding utf8`) broke the mod: `Error loading script: ...main.lua:1: unexpected symbol near '<\239>'` — `\239` (0xEF) is the first byte of a UTF-8 BOM (`EF BB BF`), which Windows PowerShell 5.1's `utf8` encoding adds by default (unlike Write/Edit tool writes, which don't). This was the third distinct PowerShell-specific footgun hit building this pipeline in one session, after `Where-Object`'s scalar-collapse (§3.11) and `ConvertFrom-Json` nesting single-element arrays unpredictably (hit while porting the armor/mods extraction, not separately written up). User correctly read this as a signal the tooling itself was fragile, not just three unlucky one-off bugs, and asked to rebuild it properly rather than keep patching around PowerShell's defaults. Result:
- **`scripts/InventoryTracker/`** (tracked in git, unlike `dev-data/` which is gitignored) — `lib.py` (shared `normalize`/`find_package`/JSON IO), `match_rings_amulets.py`/`match_armor.py`/`match_mods.py` (one per category, since the grouping logic genuinely differs — flat single-item vs. multi-piece-per-set vs. standalone-vs-weapon-embedded filtering — consolidating them would trade real complexity for a false sense of DRY), and `generate_lua.py`.
- **`scripts/InventoryTracker/wiki_data/*.txt`** — the wiki name lists, now tracked (previously untracked under gitignored `dev-data/`).
- Each match script reads `dev-data/Exports/` directly and writes `dev-data/master_list/<category>.json` (all three run independently, no shared mutable state to corrupt). `generate_lua.py` reads all of `dev-data/master_list/*.json` and **fully overwrites `InventoryTracker/Scripts/master_list_data.lua`** — a standalone `return { ... }` data file, not embedded in `main.lua` at all. `main.lua` loads it with `local MASTER_LIST = require("master_list_data")`, the standard way to split a UE4SS Lua mod across multiple files. This replaced an earlier marker-splice-into-`main.lua` design (between `-- BEGIN/END MASTER_LIST` comments) — the user correctly pushed back on that as still fragile (a full file overwrite of a dedicated data file has nothing else in it to accidentally clip, vs. finding markers inside a 600-line hand-maintained file). Considered and rejected: loading JSON directly at runtime instead of generating Lua — UE4SS's Lua API has no bundled JSON decoder (confirmed via their docs), so that would've meant shipping a hand-written JSON parser inside the mod; a plain Lua data file needs zero parser since the game's own Lua interpreter parses it natively.
- Re-ran the full pipeline in Python and confirmed identical output to the retired PowerShell scripts: 328/328 rings+amulets, 36/36 armor sets (120 pieces), 36/36 mods — same counts, same exclusions. The old `dev-data/*.ps1` scripts and their intermediate CSVs were deleted (gitignored, safely reproducible from `scripts/InventoryTracker/` + `dev-data/Exports/` at any time).
- **Any future category (Weapons, etc.) should get a new `match_<category>.py` following this pattern** — read exports directly, write `dev-data/master_list/<category>.json`, then run `generate_lua.py`. Don't reach for PowerShell for this kind of JSON/CSV data-transform work going forward; Python's stdlib (`json`, `pathlib`) doesn't have the array-collapse/encoding footguns that bit this pipeline three times.

### 3.13 MOD #4 InventoryTracker — Weapons added via remnant2.wiki.gg's Cargo API instead of FModel exports, 2026-07-28

Extended `MASTER_LIST` from 484 to **596 entries** (112 weapons: 40 long guns, 26 handguns collapsed from 27 wiki rows, 46 melee). First category built without touching `dev-data/Exports/` at all.

**Why the export approach was abandoned for this category**: the user exported `Items/Weapons/` across all `World_*` folders (checking both pakchunks, per the now-established habit) and still only reached 69/113, then 98/113 wiki-listed weapons after a second pass. Worse than the count gap: ~20 "Standard" tier weapons (starter/common-tier guns and melee) use generic internal names (`LongGuns/Standard/Shotgun`, `HandGuns/Standard/Revolver`, `Melee/Standard/Hammer/Hammer`, etc.) with no way to derive their real in-game name (`Ford's Scattergun`, `Western Classic`, `Scrap Hammer`) from the asset path alone — a bigger, more systematic version of the archetype-armor naming problem from §3.12.

**The discovery**: the user found `remnant2.wiki.gg` has a MediaWiki **Cargo-fork extension** (branded "LIBRARIAN" in `Special:Version`) storing structured per-item data, viewable per-page at `Special:DatabaseData/<PageName>` and bulk-queryable via the standard `action=cargoquery` API endpoint at `https://remnant2.wiki.gg/api.php` (note: NOT `/w/api.php` — this wiki's API lives at the site root). Example query:
```
https://remnant2.wiki.gg/api.php?action=cargoquery&tables=items&fields=name,filepath,class&where=class="Long Gun"&format=json&limit=500
```
Returns `{name, filepath, class}` per item, where **`filepath` is already the complete classPath** (`Package.ClassName_C` form, e.g. `/Game/World_Base/Items/Weapons/Longguns/Special/AlphaOmega/Weapon_AlphaOmega.Weapon_AlphaOmega_C`) — not a bare `Package` path needing the `.ClassName_C` suffix appended like FModel's raw `Package` field. **Hazard hit once already: concatenating a suffix onto an already-complete `filepath` produces a malformed double-suffixed string** (`...AlphaOmega_C.Weapon_AlphaOmega_C`) — caught before it shipped by inspecting the raw data first. The `items` table's `class` field has **25 distinct values** covering nearly every category this mod could ever want: `Ring`, `Amulet`, `Body Armor`/`Glove Armor`/`Leg Armor`/`Helmet`, `Long Gun`, `Handgun`, `Melee Weapon`, `Weapon Mod`, `Mutator`, `Engram` (likely archetypes/traits), `Relic`, `Consumable`, and more.

**This is NOT uniformly trustworthy — verify per category before relying on it**. Querying `Weapon Mod` to gauge reusing this for future categories revealed roughly 15 entries where `filepath` points to an unrelated **crafting material** instead of the mod itself (e.g. `Bore` → `Material_MutatedGrowth`, `Corrosive Rounds` → `Material_TaintedIchor`, `Knight Guard` → `Material_CrematedSoulAsh`, `Skewer 2.0` → `Material_DreadCore`) — plausibly a wiki template bug conflating "crafting material used to obtain this" with "the item's own asset," but the practical effect is the same: trusting it blindly would have silently swapped several master-list entries to track ownership of a crafting material instead of the actual mod. `Weapon Mod` data was NOT used from this source — that category stays on the already-verified FModel-built `mods.json` from §3.12. Weapons, by contrast, cross-checked clean: every one of the 113 wiki-listed long guns/handguns/melee weapons returned a real `Weapon_*.json`-shaped filepath (0 blanks, 0 obviously-wrong substitutions), and a sample (Plasma Cutter) matched the FModel-verified `Package` field exactly, modulo folder casing (`Longguns` vs the true `LongGuns` — harmless, since `main.lua`'s ownership check already lowercases both sides before comparing, per §3.11's original design). **Rule going forward**: before trusting this API for a new category, pull a sample and check for (a) blank `filepath`s and (b) `filepath`s pointing to a plausible-but-wrong asset type (`Material_*` instead of the item's own class) — don't assume clean data just because the category name looks similar to one that worked.

**Practical fallout**: `match_weapons.py` no longer touches `dev-data/Exports/` or `scripts/InventoryTracker/wiki_data/weapon_names.txt` at all (that file was deleted — dead once the script stopped reading it) — it queries the API directly for `Long Gun`/`Handgun`/`Melee Weapon`, collapses `Polygun (Marksman)`/`Polygun (Shotgun)` (one real inventory item, two wiki rows, same `filepath`) to a single `Polygun` entry, and writes `dev-data/master_list/weapons.json`. The API needs a real `User-Agent` header or `remnant2.wiki.gg` 403s the request (MediaWiki API etiquette — default/empty Python `urllib` UA gets rejected). No `dev-data/Exports/Items/Weapons/` re-export was needed once this was found — the ~30 minutes spent on the second export pass turned out to be avoidable, though it wasn't wasted: it's what surfaced the naming-gap severity that motivated finding a better source in the first place.

**Ownership model is fundamentally different from every prior category — confirmed via a live ZZTestMod F9 probe, not guessable from static data alone.** The CXX header dump (`GunfireRuntime.hpp`) surfaced `UTraitsComponent` (an `ActorComponent`, found/matched to the player pawn the same `FindAllOf`+`GetOuter` way as every other component in this mod) with a `TArray<FTraitInfo> Traits` property — `FTraitInfo` has `TraitBP` (class ref) and `Level` (int32, 0–10, the player's allocated points). - For Unlockable traits specifically: **presence in the array means "found," absence means "not found" — Level 0 is a real state ("found it, haven't spent points"), not the same as missing.** Confirmed against the user's actual character: only 7 of 22 unlockables were present in a 36-entry array: `BloodBond`(0), `Rugged`(0), `Barkskin`(10), `Handling`(0), `Amplitude`(0), plus two Archetype-tagged ones (`StrongBack`(10), `Triage`(2)) that don't count for this category. The other 15 unlockables were genuinely absent, not present-at-0 — this is the load-bearing fact that makes "presence = ownership" a safe reading.
- For Archetype traits: `Level` in this array isn't real player-allocated points at all — it mirrors the archetype's own level (confirmed by the user: `StrongBack`=10 because their Challenger is maxed, `Triage` capped at 2 because their Medic is only level 1, and they cannot manually add more to `Triage` regardless of available trait points). **Worse: all 14 `Archetype_*` entries appear in this array unconditionally, even for archetypes the character has never unlocked** (the user has only ~7 of 14 engrams, but all 14 showed up at Level 0) — so this array cannot be used to detect archetype/engram ownership at all. That's why Archetype traits are excluded from `MASTER_LIST` entirely rather than tracked with a caveat: their real ownership signal is "do I own the Engram," already covered correctly by the `Engram` category (§3.15) via the inventory-item scan.
- The array also holds unrelated entries sharing the same `UTrait` base class — Archetype Perks (`Perk_*`) and Skill Traits (`SkillTrait_*`), all Level 0, only present for archetypes the character has actually leveled. Confirmed out of scope (auto-unlock via leveling, not a findable collectible) and excluded by construction (`match_traits.py` only reads from `Trait_*.json` files, never sees these).
- `AvailableTraits` (`TArray<TSubclassOf<UTrait>>`, also on `UTraitsComponent`) was empty (length 0) on the live probe — not usable for anything, dropped as a candidate data source.

`readTraitLevels()` in `main.lua` implements this: reads `TraitsComponent.Traits` (plain property, no function call — same safety class as every other array read in this mod), builds a `classPath -> Level` map, and the F8 handler looks up `MASTER_LIST` trait entries in that map instead of the inventory-ownership check used for every other category. A trait not in the map prints with its wiki source text (`"[ ] (Trait) Chakra - Root Earth (Campaign)"`) so a missing trait tells you where to go find it; a present one prints its level (`"[X] (Trait) Barkskin - 10/10"`). In-game F8 output confirmed exact match to the live probe's findings (the same 5 non-archetype unlockables show `[X]` with correct levels, the other 17 show `[ ]` with source text).

`generate_lua.py` was generalized to carry any extra string-valued key through to the Lua table generically (traits' `source` field), instead of hardcoding the `{category, name, classPath}` triple — reusable for any future category needing an extra display field without another schema bump.

### 3.17 MOD #4 InventoryTracker — bare-UMG widget construction from pure Lua, no existing Blueprint template needed

Investigated via the same incremental ZZTestMod-probe discipline as every other risky operation in this project, since nothing this size (a many-row scrollable panel) had been attempted before — the only prior widget-construction precedent, `MoreLoadoutSlots`' extra loadout tiles, reused an *existing* game Blueprint class as a template. This confirms the same techniques work building entirely from bare engine classes with no template asset at all. (Project-planning context — what this unlocks/doesn't for InventoryTracker specifically, and the decision to defer part of that mod's UI — lives in `TODO.md`, not here; this section is the reusable modding technique only.)

**Confirmed hard blocker: clickability.** UE4SS Lua cannot bind `MulticastInlineDelegateProperty` — already known from `MoreLoadoutSlots` (§3.4o: reading `newTile.OnClicked` itself throws `Property type 'MulticastInlineDelegateProperty' not supported`, an error that pierces `pcall`). That mod worked around it by hook-forwarding an *existing Blueprint-compiled* click-handler function — no such function exists to hook for a widget built from scratch in Lua, so a native `Button` constructed this way is worse off than that case, not equally blocked. Any mod needing real clickable buttons/tabs/links built purely from Lua-constructed native widgets is blocked by this; only a Blueprint-asset-based widget (real compiled delegates) or a hook-forwarding trick against an *existing* Blueprint click handler sidesteps it.

**Bare-UMG construction recipe, proven live across ZZTestMod probe rounds (screenshots confirmed each round):**
1. **Root widget**: `StaticConstructObject(StaticFindObject("/Script/UMG.UserWidget"), playerController)`. **Its auto-populated `.WidgetTree` is NOT writable** — assigning `.RootWidget` on it fails with `Tried setting member variable 'RootWidget' but UObject instance is nullptr` (silent to `pcall` — this is a UE4SS-level log message, not a Lua error, so the write appears to "succeed" while doing nothing). Root cause (inferred, matches the fix): `WidgetTree` is normally an *instanced* subobject — each real `UserWidget` gets its own private copy at proper construction time — and raw `StaticConstructObject` skips that instancing step, leaving the auto-read value pointing at a shared/default template object the engine refuses to mutate. **Fix**: construct your own `WidgetTree` (`StaticConstructObject(StaticFindObject("/Script/UMG.WidgetTree"), newPanel)`) and assign it yourself (`newPanel.WidgetTree = ourTree`) before touching anything else. Confirmed working immediately once done this way.
2. **Child widgets** (`TextBlock`, `ScrollBox`, `VerticalBox`, `HorizontalBox`, `Border`, `SizeBox`) — all plain engine classes (`/Script/UMG.*`), all constructible the same way (`StaticConstructObject(class, ourTree)`) and nestable via ordinary `:AddChild()` calls. Same category of operation already proven in `MoreLoadoutSlots` (§3.4v, splicing a `ScrollBox` into an existing live tree) — engine widgets have no Blueprint-only `Initialize()`-time delegate bindings to miss, unlike a Blueprint widget class (which forced `WidgetBlueprintLibrary.Create` there). Confirmed at 30 constructed rows (60 `TextBlock`s + 30 `HorizontalBox`es + 1 `VerticalBox`) with zero failures.
3. **Colored text**: `TextBlock.ColorAndOpacity` is an `FSlateColor` (`{SpecifiedColor: FLinearColor, ColorUseRule}`, confirmed via `SlateCore.hpp`). Uses the struct write-back rule already documented in §3.4bb (read into a local, mutate the local's nested fields, assign the WHOLE struct back — in-place mutation of the original reference silently doesn't apply) — `color.SpecifiedColor.R/G/B/A = ...; color.ColorUseRule = 0; textBlock.ColorAndOpacity = color`. §3.4bb proved this pattern on an *existing live* game widget two weeks earlier; this confirms it works identically on a *freshly Lua-constructed* one.
4. **Fixed sizing**: raw `SizeBox.HeightOverride`/`WidthOverride` writes do nothing, per the already-known H4/§3.4i hazard (Slate caches desired size separately from the property) — must call the real `SetHeightOverride()`/`SetWidthOverride()` setters (plain float arguments, low end of the function-call risk tier). Confirmed the setters DO take effect (content laid out to the requested width).
5. **Background**: `Border.BrushColor` (`FLinearColor`) via the same write-back pattern as step 3, deliberately *not* the `SetBrushColor(FLinearColor)` function call (a struct passed *by value* to a function — this project's riskiest call category, same class as the `HasItem`/`TSoftClassPtr` crash). Confirmed a default renderable brush already exists on a bare-constructed `Border` (`UBorder`'s own C++ constructor still runs under `StaticConstructObject` — it's specifically Blueprint-compiled `Initialize()`/delegate-binding steps that get skipped, not the base constructor) — tinting via write-back alone was enough, no brush assignment needed.

**Three more problems found and solved (rounds 3-6, all confirmed via screenshot/log, 2026-07-28):**
6. **A `Border`/`SizeBox` placed *outside* a `SizeBox` still paints unbounded.** First attempt had `Border → SizeBox(900×500) → ScrollBox → VerticalBox → rows`; the `SizeBox` correctly constrained the *content* to 900px width, but the `Border`'s background tint washed across the **entire screen**. Cause: `Border` was the outer/root element with no size constraint of its own — a `UserWidget` added via `AddToViewport` fills the whole viewport by default (stretch anchors), so anything with no size limit of its own stretches to fill that whole space regardless of what its *children* are constrained to. **Fix**: put the `SizeBox` OUTERMOST instead (`SizeBox → Border → ScrollBox → ...`) — bounds the content correctly, but see problem 7, this alone wasn't enough to bound the *whole panel*.
7. **Even with the `SizeBox` outermost, the whole panel still covered the entire screen.** The `SizeBox`'s own `Width/HeightOverride` bounds its *desired* size, but `AddToViewport` gives the widget a `UCanvasPanelSlot` with default full-stretch anchors — the slot forces the widget to fill the whole viewport rect regardless of its own desired size. The natural fix (`UCanvasPanelSlot.bAutoSize`, a **plain bool property** — no struct, no function call) turned out to be unreachable: writing it, both synchronously right after `AddToViewport` and after polling the slot reference for up to 2 seconds (`LoopAsync(50, ...)`, the same pattern that fixed problem 1's `WidgetTree` timing issue), always failed with `Tried setting member variable 'bAutoSize' but UObject instance is nullptr`. Unlike the `WidgetTree` case, this was **not** a timing problem that polling could fix — `AddToViewport`'s `UCanvasPanelSlot` appears to just not be reliably exposed to Lua writes in this build, full stop. **Working fix**: don't fight the viewport slot at all. Make an `Overlay` (fills the screen, invisible, no size constraint needed — that's fine, it has no visible content of its own) the actual `RootWidget`, then `overlay:AddChild(sizeBox)` instead of relying on `AddToViewport`'s own slot. `AddChild`-populated slots (`UOverlaySlot` here) have been reliable every single time in this project (`.Slot` reads and writes cleanly right after `AddChild`, unlike right after `AddToViewport`) — set the child's alignment via `slot:SetHorizontalAlignment(1)`/`SetVerticalAlignment(1)` (`HAlign_Left`/`VAlign_Top`, plain `TEnumAsByte` enum arguments — low risk, same tier as `SetHeightOverride`). Confirmed working: panel renders as a properly bounded 900×500 box in the top-left corner instead of covering the screen.
8. **Mouse-wheel input passed straight through to character/camera control.** Distinct from the `ScrollBox`'s own scroll behavior — an input-*routing* problem: `AddToViewport` only renders the widget, it doesn't change where input goes. Found `UWidgetBlueprintLibrary::SetInputMode_GameAndUIEx(PlayerController, WidgetToFocus, EMouseLockMode, bHideCursorDuringCapture, bFlushInput)` via the CXX header dump (`UMG.hpp`) — the reflected Blueprint-node equivalent of the native-only (non-reflected, hence absent from the header dump entirely) `APlayerController::SetInputMode()`. Crucially it takes **only plain types** (object pointers, an enum as a plain int, bools) — not the `FInputModeGameAndUI` struct the raw C++ API uses — sidestepping the struct-by-value function-argument risk class entirely (same category as the `HasItem`/`TSoftClassPtr` crash). Call it after `AddToViewport` with `EMouseLockMode.DoNotLock` (0) and pair with `PlayerController.bShowMouseCursor = true` (plain bool property); restore with `SetInputMode_GameOnly(PlayerController, false)` + `bShowMouseCursor = false` when the panel closes. `GameAndUI` mode (not `UIOnly`) was chosen so keyboard still drives the character while mouse also reaches the widget tree. **Confirmed working**: scrolling now responds to the mouse wheel, character movement still works via keyboard.

**End state, all three problems solved together**: `Overlay` (RootWidget, full-screen, invisible) → `AddChild` → `SizeBox` (900×500, aligned top-left via its `UOverlaySlot`) → `Border` (background) → `ScrollBox` → `VerticalBox` → rows, plus `SetInputMode_GameAndUIEx` after `AddToViewport`. User-confirmed screenshot: a correctly bounded, colored, scrollable 30-row panel in the top-left corner, mouse wheel scrolling working, character still controllable. This is now a complete, proven recipe for a bare-Lua UMG panel.

**Shipped into `InventoryTracker/Scripts/main.lua`, 2026-07-28** — real `MASTER_LIST` data (699 entries, all 8 categories) replacing the 30 test rows, `Page Up`/`Page Down` category switching, and a header status line. Two more findings surfaced during that final wiring pass:

9. **A raw `.Text` write on a widget that's already live in the tree (already `AddChild`'d and already rendered via `AddToViewport`) doesn't reliably update — even though every other raw property write in this recipe worked fine.** The header line's text is updated in place every time the category switches (the widget stays the same, only its content changes), and a plain `headerText.Text = FText(...)` silently did nothing visually despite `pcall` reporting success. Root cause matches the already-known H4/§3.4bb rule generalized one step further: "raw writes are only safe for plain data Slate doesn't need to react to" applies to *text content* too, not just layout properties like `HeightOverride` — but only once the widget is already on screen. Row text never hit this because it's always set *before* `AddChild`, the safe ordering §3.4bb already recommends. **Fix**: call the real `SetText(FText(...))` function instead of the property write for any text that updates on an already-displayed widget. `FText(...)`-wrapped exactly as already established safe (§3.4b) — this is a function call, but a plain-`FText`-parameter one, not a struct-by-value one.
10. **UE4SS's `Key` table uses underscore-separated ALL-CAPS names, not camelCase.** `Key.PageUp`/`Key.PageDown` don't exist — the mod failed to even load (`RegisterKeyBind:448: No overload found for function 'RegisterKeyBind'`, since a `nil` first argument matches no overload) until corrected to `Key.PAGE_UP`/`Key.PAGE_DOWN`. Full name list: `docs.ue4ss.com/lua-api/table-definitions/key.html`. `Key.F8`/`Key.F9` happened to already be correct (single letters/numbers don't have a naming-convention question), which is why this didn't surface until a non-alphanumeric key was needed for the first time in this project.

### 3.18 MOD #4 InventoryTracker — investigating real clickable links via `RegisterHook`, in progress 2026-07-30

The §3.17 clickability blocker is specifically about *binding a `MulticastInlineDelegateProperty`* (e.g. `Button.OnClicked`) — confirmed this is a property-type gap in UE4SS's Lua reflection bridge, not a statement that Unreal itself lacks the feature, and not specific to `Button` as a class (any `BlueprintAssignable` event property hits the same error, on any widget). Before committing to the keyboard-selection fallback design, investigating whether `RegisterHook` — a completely different mechanism, already proven in this project (`EquipmentSearch`'s `OnAddedToFocusPath`/`OnRemovedFromFocusPath` hook, §3.6c) — can detect a mouse click on a specific row widget without ever touching a delegate property.

**Desk research findings (UE4SS docs + GitHub, before writing a probe):**
- `RegisterHook` operates on **`UFunction`s only**, not delegate properties — confirmed directly: "RegisterHook doesn't support delegate functions" ([UE4SS docs](https://docs.ue4ss.com/lua-api/global-functions/registerhook.html)). This is a genuinely separate code path from delegate binding, not an alternate route to the same blocked mechanism.
- Signature: `RegisterHook(path, preCallback, postCallback)`. For `/Script/`-prefixed paths, `preCallback` runs *before* the native function executes and `postCallback` (optional) runs *after* and can read/override the return value; for non-`/Script/` paths the first callback runs after and the second is ignored. Callback shape is `function(self, ...params)` — `self` is the calling object instance, which is exactly what's needed to filter a hook on a shared base class down to "did this fire for *our* specific row widget."
- The target `UFunction` must already exist/be loaded in memory at registration time (same category of constraint as the project's other `NotifyOnNewObject`-timing gotchas, §3.4k/3.4t/3.8).
- **Precedent for hooking a base engine UMG class (not just a Remnant2-specific Blueprint subclass) exists publicly**: `RegisterHook("/Script/UMG.UserWidget:Construct", function() ... end)`. This matters because our case would hook the base `/Script/UMG.Widget` class (since our rows are bare-constructed, not a Blueprint subclass) — a bigger blast radius than the `EquipmentSearch` precedent (which only hooked one specific Blueprint subclass), since a base-class hook fires for every widget of that type in the whole game, filtered down only by the `self` check inside the callback. Confirmed this pattern is used elsewhere, not just theorized.

**Live probe results, 2026-07-30 — click detection via `RegisterHook` is a dead end; `LaunchURL` works fine.**
- Round 1: guessed two candidate function paths (`Widget:OnMouseButtonDownEvent`, `Widget:NativeOnMouseButtonDown`). Both failed outright at registration — `"no UFunction with the specified name was found"` — confirming neither is real/reflected under those names.
- Round 2: rather than guess a third name, enumerated real functions via `class:ForEachFunction(callback)` (iterates every `UFunction` on a class/struct; callback receives the `UFunction` object, `fn:GetFName():ToString()` gives its name — a completely safe, read-only reflection query). Found `OnMouseButtonDown`/`OnMouseButtonUp`/`OnMouseButtonDoubleClick`/`OnMouseMove`/`OnMouseEnter`/`OnMouseLeave`/`OnMouseCaptureLost`/`OnMouseWheel`/`OnPreviewMouseButtonDown` — but **only on `/Script/UMG.UserWidget`**, not on `/Script/UMG.Widget` or `/Script/UMG.TextBlock`. Mouse events are a `UserWidget`-level concept only; individual leaf widgets like `TextBlock` don't have their own click entry points in reflection at all.
- Round 3: since only `UserWidget` gets click events, tested wrapping a row's `TextBlock` in its own nested `UserWidget` (same `StaticConstructObject` + own `WidgetTree` recipe as the top-level panel, one level deeper as an `AddChild`'d child) — the idea being `self` inside a `RegisterHook("/Script/UMG.UserWidget:OnMouseButtonDown", ...)` callback would directly identify which row's wrapper was clicked, no geometry hit-testing needed. `RegisterHook` registered with no error. **Never fired, not even once, when clicking directly on the wrapped text.**
- Round 4: to rule out "wrong widget" vs. "mechanism doesn't work at all," tested clicking real, already-built game UI while the same hook stayed registered: interactive character-menu buttons/icons (still silent — plausible explanation: `SButton`-internal widgets mark the click "handled" and it never bubbles up to the parent `UserWidget`), and — the deciding test — **blank, non-interactive background space in a full-screen menu (still silent)**. A blank area has nothing to consume/handle the click first, so this is the cleanest possible test of whether `OnMouseButtonDown` fires via `RegisterHook` at all in this build, for any target. It doesn't.
- Separately, the project's own "known-good" sanity hook (`UserWidget:Construct`, the public precedent from §3.18's desk research) also never fired during this same session — but that's explainable and not corroborating evidence of a broader `RegisterHook` failure: `Construct` only runs once per widget instance, and Remnant 2's menus are very likely already-constructed and just shown/hidden after the first session-wide open (matches the known first-open-only construction quirk, §3.4k/3.8), so no new `Construct` calls were expected during this test regardless.
- **`UKismetSystemLibrary::LaunchURL(FString)` is confirmed working** — found via `StaticFindObject("/Script/Engine.Default__KismetSystemLibrary")` (the class default object, same pattern as `Default__WidgetBlueprintLibrary` elsewhere in this project), called as `ksl:LaunchURL(url)` with a plain Lua string (auto-marshaled, no `FText`/`FString` wrapper needed — unlike `FName`/`FText` params elsewhere in this project). **User-confirmed: a real browser tab opened** to the target URL. This half of the "clickable link" problem is solved and reusable regardless of what triggers it.

**Conclusion: real point-and-click links are not achievable from pure Lua in this UE4SS build** (at least not via this `RegisterHook` route — exhausted after 4 rounds/3 distinct target types with zero fires, treating further guessing as diminishing returns rather than a proof of impossibility). The `LaunchURL` half works and is trivially reusable by any *other* trigger mechanism — e.g. keyboard-driven row selection + Enter, the fallback design proposed before this investigation started (`TODO.md`).

### 3.19 LoadoutNamer — per-character identity found: `GameInstance.CharacterManager:GetActiveCharacter().ID`, 2026-08-04

**Bug**: `LoadoutNamer` stored names keyed only by `recordIndex` (0-20), with no notion of which of the game's 4 character-select slots owned them, so a name set on one character showed up on every character (one shared `loadout_names.txt`). User-confirmed via the "SELECT CHARACTER" screen (four tabs, I-IV) that characters have no player-typed names — only slot position — so the fix needed a slot **index**, not a name.

**Found via ZZTestMod `F9` probe** (read-only, `ExecuteInGameThread`, no mutation): neither `PlayerController`, `PlayerState`, nor `GameInstance`'s own leaf Blueprint properties had anything slot-related — `ForEachProperty` only sees a class's *own* declared properties, not inherited ones (same lesson as §EquipmentSearch's struct `GetSuperStruct()` walk), so the first probe pass (leaf class only) came back empty across all four candidate objects. Walking the full native inheritance chain via `GetSuperStruct()` (up to 20 levels) surfaced `CharacterManager` (an `ObjectProperty`) on both `GameInstance` (as `RemnantGameInstance.CharacterManager`) and the player `Pawn` (as `CharacterGunfire.CharacterManager`) — name alone was the strongest lead in the whole scan.

- `GameInstance.CharacterManager` is a **`RemnantCharacterManager`**. `TransientCharacters` (array) is empty during normal play (likely only populated during the character-creation flow) — a dead end. `ForEachFunction` (enumeration only, no calls, same safe pattern as §3.18 round 2) listed real functions including `GetActiveCharacter`, `HasActiveCharacter`, `GetCharacterCount`, `GetCharacterAt`, `SetActiveCharacter`.
- `charMgr:HasActiveCharacter()` → `true`; `charMgr:GetActiveCharacter()` returns a **`SavedCharacter`** struct/object with an **`ID` `IntProperty`** — confirmed **`0`** on the first character-select slot and **`1`** on the second, in the same session, via two separate F9 probe runs before/after switching characters at the main menu. This is exactly the per-slot identifier needed. `SavedCharacter` also carries its own `Name` (`StrProperty`, always empty/unset — matches "characters have no typed name"), `LoadoutRecords` (its own array, separate from the live `LoadoutComponent`), `Level`, `PowerLevel`, `TraitRank`, etc.
- Both calls are **non-mutating, no-arg getters** — read-only, the safe end of the risk ladder; no crash across ~5 F9 probe invocations in one session (including immediately after a character switch / world reload).
- **`FString`/`FName` property values print as opaque userdata handles** (`FString: 0x...`) unless you call `:ToString()` on them — `tostring()` alone is not enough. Cost real probe cycles here (`SavedCharacter.Name`, `PlayerState.SavedNetworkAddress` etc. all printed as pointers on the first pass) before the fix.

**Fix applied** (`LoadoutNamer/Scripts/main.lua`): `resolveActiveCharacterID()` (finds the first non-`Default__` `GameInstance`, reads `.CharacterManager`, calls `HasActiveCharacter()`/`GetActiveCharacter()`, returns `.ID` or `nil`) is called at the top of the apply pass (`applyNamesToCount`, already on the game thread) — cheap enough to re-resolve on every Loadouts-screen construction rather than cache indefinitely, which is what makes a character switch (a full world reload) immediately pick up the right character's names. The name store became `names[characterID][recordIndex]`, file format `characterID<TAB>recordIndex<TAB>name`. Old-format (`recordIndex<TAB>name`) lines are parsed into a `legacyNames` bucket and merged into whichever character resolves first after the update (user-decided migration behavior, since the old format can't say which character a name actually belonged to).

### 3.20 MOD #5 PrismLegendaryReroller — legendary-bonus cleanse no longer costs a relevel, 2026-08-04

**Goal**: Prisms cap at level 51, at which point a legendary (Mythic) bonus is rolled from a pool. Rerolling it ("cleanse") vanilla-resets the Prism to level 50, forcing a full relevel grind before you can roll again. User wanted that regression removed — distinct from the separate "cleanse the whole Prism" action (full reset to level 0, clears every rolled stat segment too), which was explicitly **not** in scope and is left untouched.

**No FModel export exists for Prisms in `dev-data/`** — this was genuinely unresearched territory. Found the real class data via the **`CXXHeaderDump`** UE4SS generates at `<game>/Binaries/Win64/ue4ss/CXXHeaderDump/*.hpp` (not previously used as a lookup source in this project's ladder — add it alongside FModel dumps as a step-1 grep target; same trust tier, sourced from the live binary's reflection data instead of the paks). `grep -ril prism` over that directory immediately surfaced the whole class family (`PrismStone_Base.hpp`, `PrismOfGreed.hpp`/`PrismOfHatred.hpp`/etc. — 7 Prisms, one Blueprint subclass each of a shared native base — plus the relevant UI widgets).

**Class chain**: `APrismOfGreed_C` (and the other 6) → `APrismStone_Base_C` (Blueprint, near-empty) → `APrismStone` (native, in `Remnant.hpp`, ~90 reflected functions). Persistent save data lives in `UPrismStoneInstanceData` (`CurrentSegments: TArray<FPrismSegment>`, `CurrentSeed`, `PendingRoll`, `CurrentFeedData`, `PendingExperience`/`PendingMaxExperience`) — **no stored "Level" field at all**; `GetPrismStoneLevel()`/`GetPrismStoneExperienceLevel()` are pure computed getters.

**Two distinct native functions, confirmed by live probe (not guessable from the header alone — this correction came from the user, who knows the two cleanse actions are separate in-game features)**:
- `ServerFlushSegment(int32 SegmentIndex, int32 NumRefundLevels)` — flushes **one** segment by index. This is the legendary-only cleanse.
- `ServerFlushPrismStone(bool RemoveSegments, bool RemovePendingExp, bool RemoveFeedData, bool RemoveStoredLevels)` — the whole-Prism reset. Not touched by this mod.

**ZZTestMod probe, hooking both (`RegisterHook("/Script/Remnant.PrismStone:ServerFlushSegment", ...)` etc.)** — first hook attempt nested registration inside a `ClientRestart` hook (this project's usual pattern for gameplay hooks) and it **never fired on a hot-reload**: `ClientRestart` already fired earlier in that play session (character already spawned), and hot-reload doesn't respawn the character. Moved registration to **top level** (no `ClientRestart` wrapper) since `APrismStone` is a native engine class — its UFunctions are already resident at script-load time, unlike Blueprint/widget classes which need an instance or spawn event first. Top-level registration fired immediately and correctly. **Lesson for future native-class hooks: register at top level, only nest inside `ClientRestart` for Blueprint/gameplay-instance-dependent hooks.**

**Confirmed via F9 (state dump) + hook logging, real in-game legendary cleanse**: `ServerFlushSegment(SegmentIndex=5, NumRefundLevels=0)` fired. Before: `PrismStoneLevel=51, NumSegments=6, HasMythicSegment=true`. After: `PrismStoneLevel=50, NumSegments=5, HasMythicSegment=false`. **`NumRefundLevels` was 0 — the level drop is not parameter-driven.** Since `PrismStoneLevel` is a computed value with no backing field, the most consistent read is that it's derived from segment content (the Mythic segment appears to carry exactly 1 level's worth), and removing it via `ServerFlushSegment` naturally recomputes the total down by 1 as a side effect, not an explicit decrement.

**Fix, confirmed end-to-end**: rather than trying to suppress a parameter that doesn't control the behavior, restore the level afterward through the game's own leveling machinery (per the CLAUDE.md rule to prefer that over reimplementing game logic) — `GetExperienceRequiredForLevel(51)` + `AddExperience()` (the same function combat kills/feeding use). Manually triggered via an F11 test keybind first: read the required experience, call `AddExperience()`, F9 confirmed `PrismStoneExperienceLevel` back to 51 and **`CanRoll` flipped from `false` to `true`** — and the user was able to roll and pick a new legendary bonus immediately in-game, no relevel needed.

**Detecting "this is a legendary flush" (vs. a regular non-Mythic segment reroll, which also goes through `ServerFlushSegment` but with a real `NumRefundLevels` cost)**: reading `GetPrismStoneLevel()` **synchronously inside the pre-hook, before the real flush runs** (native `/Script/` paths are pre-hooks — the call already exists in the header this way; `/Script/` prefix vs `/Game/` prefix pre/post distinction is documented in §3.4). `preLevel == 51` is a reliable signal because a Mythic segment can only exist on a Prism that reached 51 in the first place — no need to inspect the segment's row name or category at all. This was tested as a standalone novel operation before being made load-bearing: **calling a native no-arg getter synchronously inside a `RegisterHook` callback body, after `self:get()`, is safe** (no crash across the test) — every prior hook in this project's mods only read wrapped param values or plain properties directly in the hook body, deferring any further native calls via `ExecuteInGameThread` (H8's caution was specifically about touching the raw un-`self:get()`'d wrapper, not about calls after unwrapping — but this distinction was unconfirmed until this probe). Established pattern going forward: a single no-arg reflected getter call in a hook body is safe to test incrementally the same way; still defer anything mutating (like `AddExperience`) via `ExecuteInGameThread`.

**Feature code**: `PrismLegendaryReroller/Scripts/main.lua`. Hooks `ServerFlushSegment` (top-level, native path), checks `preLevel == 51` synchronously in the hook, and if so defers to `ExecuteInGameThread` a call to relevel back to 51 via `AddExperience(GetExperienceRequiredForLevel(51))`.

### 4.1 Critical gotcha: AAM's bundled UE4SS is known to go stale
Community consensus (posts as recent as June 2026) is that the AAM zip's bundled UE4SS build regularly falls behind the game's current patch, causing summon commands / mods to silently stop working even though the console still opens. **Fix used by the community**: manually download the latest **non-experimental, non-dev, non-experimental-latest** release from `github.com/UE4SS-RE/RE-UE4SS/releases`, and replace ONLY two files in the flat `Win64` folder — `UE4SS.dll` and `dwmapi.dll` — leaving everything else from AAM (settings, Mods folder, other DLLs) untouched.
- **Do NOT** switch to the newer `ue4ss/` subfolder layout (introduced in UE4SS 4.0+) for Remnant 2 — AAM and the existing R2 mod ecosystem all still expect the legacy flat layout (`Win64\Mods\`, `Win64\UE4SS-settings.ini`, `Win64\UE4SS.dll`, `Win64\dwmapi.dll` all directly in the same folder as `Remnant2-Win64-Shipping.exe`). UE4SS maintains backward compatibility with this legacy location, so this is a supported combination, not a hack — just don't "upgrade" the folder layout on your own.

### 4.2 Setup checklist (in order)

1. **Locate the right folder.** `Steam\steamapps\common\Remnant2\Remnant2\Binaries\Win64\` — this is the folder that contains `Remnant2-Win64-Shipping.exe` (the *actual* large executable, not a launcher wrapper). Everything UE4SS/AAM-related goes here, flat, no subfolder.
2. **Verify/update UE4SS to latest stable.** Download the latest tagged release (not `experimental-latest`, not a `zDEV` build unless doing C++ mod dev) from `github.com/UE4SS-RE/RE-UE4SS/releases`. Replace `UE4SS.dll` and `dwmapi.dll` in the Win64 folder with the ones from that zip. Leave `UE4SS-settings.ini` and the `Mods` folder from AAM as-is (don't overwrite `UE4SS-settings.ini` unless troubleshooting, since AAM's version and the new one may have different keys).
3. **Confirm AAM's own components are present**: console enabler + blueprint mod loader. These should already be in the `Mods` folder from AAM's own install — check `Win64\Mods\mods.txt` and confirm the relevant lines aren't set to 0 (per AAM's own instructions from earlier research).
4. **Enable the debug GUI / Live View** — edit `UE4SS-settings.ini` in the Win64 folder:

   GuiConsoleEnabled = 1
   GuiConsoleVisible = 1

5. **Launch the game once, get to the main menu, close it.** This lets UE4SS generate its first-run files/log. Confirm `UE4SS.log` exists in the Win64 folder with a fresh timestamp and no fatal errors — this is the standard "did it actually load" check.
